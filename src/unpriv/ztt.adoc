[[ztt-family]]
== Ztt Family of Attached Matrix Extensions

The Ztt family of attached matrix extensions accelerates matrix multiplication and the surrounding elementwise, conversion, and reduction operations for machine-learning and high-performance computing workloads.
An attached matrix unit has its own architectural tile registers and is operated on by instructions in the hart's instruction stream, in program order.
The extensions do not depend on the vector extensions.

// Scope: what the family is, what it is not (no new vector state, no dependency on V),
// and its dependency on the 64-bit encoding of the long-instruction extension (Zl).
// One paragraph per point; normative statements tagged Ztt_*.

[NOTE]
====
// Rationale: datatypes are a property of the instruction; registers are untyped
// containers; geometry is the only implementation parameter visible to software.
====

[[ztt-params]]
=== Implementation-defined Constant Parameters

[#norm:Ztt_N]#Each hart that implements a Ztt extension defines one parameter, the tile side _N_, which must be a multiple of 4.#
// OPEN (decision 17): the minimum N.

_N_ sets the number of elements a register holds and the inner dimension of a matrix multiply.
It does not change which registers an operand occupies.

NOTE: A row of packed 6-bit elements (four in three bytes) or of 2-bit elements (four per byte) is a whole number of bytes only when _N_ is a multiple of 4.

Ztt supports binary code that executes on harts with different values of _N_, provided the harts support the datatypes and instructions it uses.

NOTE: Thread contexts with live Ztt state cannot be migrated between harts with different values of _N_.

[[ztt-model]]
=== Attached Matrix Programmer's Model

[#norm:Ztt_state]#Ztt adds to each hart 32 matrix registers, `m0` to `m31`, _R_ accumulator registers, `acc0` to ``acc``__R__``−1``, and the read-only CSR csr:amenlen[].#
A matrix multiply reads its operands from matrix registers and accumulates into an accumulator register; the other operations read and write matrix registers.

[[ztt-mregs]]
==== Matrix Registers

[#norm:Ztt_mreg]#Each matrix register holds _N_ {times} _N_ 16-bit elements.#
<<ztt-operands>> describes how operands of other widths occupy matrix registers.

[[ztt-accregs]]
==== Accumulator Registers

[#norm:Ztt_accreg]#Each accumulator register holds _N_ {times} _N_ 32-bit elements.#
[#norm:Ztt_R]#The number of accumulator registers, _R_, is fixed by this specification.#
// OPEN (decision 6): R = 16 or 32; the evaluation also covers R = 4.

[[ztt-mstatus]]
==== Ztt Context Status in csr:mstatus[]

[#norm:Ztt_mstatus_ts]#A Ztt context-status field, csr::[ts], is added to csr:mstatus[][26:25] and shadowed in csr:sstatus[][26:25].
It is defined analogously to the floating-point context-status field, csr::[fs].#
// TS (tile status); MS is used by Zvt.

[#norm:Ztt_mstatus_ts_off]#Attempts to execute any Ztt instruction, or to access csr:amenlen[], raise an illegal-instruction exception when csr:mstatus[ts] is Off.#

[#norm:Ztt_mstatus_ts_dirty]#When csr:mstatus[ts] is Initial or Clean, executing any instruction that changes Ztt state changes csr:mstatus[ts] to Dirty.
Implementations may also change csr:mstatus[ts] from Initial or Clean to Dirty at any time, even when Ztt state does not change.#

[#norm:Ztt_mstatus_sd]#If csr:mstatus[ts] is Dirty, csr:mstatus[sd] is 1; otherwise, csr:mstatus[sd] is set in accordance with existing specifications.#

[[ztt-vsstatus]]
==== Ztt Context Status in csr:vsstatus[]

[#norm:Ztt_vsstatus_ts]#When the hypervisor extension is present, a Ztt context-status field, csr::[ts], is added to csr:vsstatus[][26:25].
It is defined analogously to the floating-point context-status field, csr::[fs].#

[#norm:Ztt_vsstatus_ts_off]#When V=1, both csr:vsstatus[ts] and csr:mstatus[ts] are in effect: attempts to execute any Ztt instruction, or to access csr:amenlen[], raise an illegal-instruction exception when either field is Off.#

[#norm:Ztt_vsstatus_ts_dirty]#When V=1 and neither csr:vsstatus[ts] nor csr:mstatus[ts] is Off, executing any instruction that changes Ztt state changes both fields to Dirty.
Implementations may also change csr:mstatus[ts] or csr:vsstatus[ts] from Initial or Clean to Dirty at any time, even when Ztt state does not change.#

[#norm:Ztt_vsstatus_sd]#If csr:vsstatus[ts] is Dirty, csr:vsstatus[sd] is 1; otherwise, csr:vsstatus[sd] is set in accordance with existing specifications.#

Context management, including saving, restoring, and virtualizing Ztt state, is specified by ext:ssttctx[].

[[ztt-discard]]
==== Context Discard

[#norm:Ztt_mdiscard]#The insn:mdiscard[] instruction raises an illegal-instruction exception if csr:mstatus[ts] is Off, or, when V=1, if csr:vsstatus[ts] is Off.
Otherwise, it sets csr:mstatus[ts] to Initial, and, when V=1, csr:vsstatus[ts].#
[#norm:Ztt_mdiscard_state]#After insn:mdiscard[], the contents of all `m` and `acc` registers are UNSPECIFIED.#

NOTE: insn:mdiscard[] need not write the registers.
Software executes it where its use of Ztt state ends, so that the state is not saved on a context switch and an implementation can reclaim its storage.

[[ztt-amenlen]]
==== Tile Side (csr:amenlen[]) Register

[#norm:Ztt_amenlen]#The _XLEN_-bit-wide read-only CSR csr:amenlen[] holds _N_.#
// OPEN: CSR address, in the unprivileged read-only range next to vlenb.

NOTE: The value in csr:amenlen[] is a design-time constant in any implementation.

[[ztt-fcsr]]
==== Floating-Point Exception Flags and Rounding Mode

[#norm:Ztt_fflags]#Floating-point exceptions raised by Ztt instructions accrue in csr:fflags[], and the DYN rounding mode is that in csr:frm[].#
Ztt has no exception-flag or rounding-mode state of its own.

[#norm:Ztt_fs]#For the purposes of csr:mstatus[fs] and csr:vsstatus[fs], a Ztt instruction that names a floating-point datatype is a floating-point instruction that writes csr:fflags[].#
// OPEN: dependency of the floating-point datatypes on F or Zfinx (cf. Zve32f).

NOTE: A matrix unit that completes Ztt instructions after the hart has retired them can merge their flags into csr:fflags[] late and in any order, because accrued flags never trap.
Only accesses to csr:fflags[] and csr:fcsr[] must be ordered with older Ztt instructions: a read must observe their flags, and a write must not be overtaken by them, which an implementation may ensure by waiting for them to complete.
csr:frm[] can be read when an instruction issues.
Decoupled vector implementations face the same requirement.

[[ztt-zvt]]
==== Coexistence with Zvt

[#norm:Ztt_Zvt_disjoint]#Ztt state and Zvt tile state are disjoint: no Ztt instruction reads or writes Zvt tile state, and no Zvt instruction reads or writes Ztt state.#
Each has its own context-status field.

NOTE: An implementation may share physical storage between the two, but must preserve both while both are live, for example by spilling one.
A context status of Initial indicates that the corresponding state need not be preserved.

[[ztt-type-codes]]
==== Type Codes

Datatypes are named by 5-bit type codes.
For integer datatypes, bit 4 is 0, bits 3:1 are log~2~ of the width minus 1, and bit 0 is set for unsigned datatypes.
Floating-point type codes have bit 4 set and are enumerated.

[#norm:Ztt_e8m0]#E8M0 encodes the power of two 2^__e__−127^ for exponent field _e_ < 255; it has no zero and no subnormals.#

[#norm:Ztt_tf32]#A TF32 element is an FP32 element whose 13 least-significant mantissa bits are treated as zero.

[#norm:Ztt_fp_subnormals]#Subnormal values are honored as operands and produced as results for every datatype that has them; there is no flush-to-zero mode.#

[[ztt-rounding]]
==== Rounding Modes

[#norm:Ztt_rm]#The `rm` field selects how a result that is not exactly representable in the destination datatype is rounded.
It takes the integer encodings when the source and destination datatypes are all integer datatypes, and the floating-point encodings otherwise.#

[[ztt-rm-table]]
.Rounding mode encoding.
[%autowidth,float="center",align="center",cols="^,<,<",options="header"]
|===
|`rm` |Floating-point encodings |Integer encodings
|000 |RNE |RNU
|001 |RTZ |RNE
|010 |RDN |RDN
|011 |RUP |ROD

|101 |ROD, round to odd |_Reserved_
|110 |_Reserved_ |_Reserved_

[#norm:Ztt_rm_rod_int]#ROD is reserved when the destination datatype is an integer datatype.#

[[ztt-saturation]]
==== Saturation

[#norm:Ztt_sat_int]#For an integer destination datatype, `sat` = 1 clamps a result that is out of range to the nearest representable value, and `sat` = 0 wraps it modulo 2^_n_^.#
[#norm:Ztt_sat_fp2int]#A conversion from a floating-point to an integer datatype always saturates as in F, and raises NV when the source is NaN or out of range; `sat` = 0 is reserved for it.#

[#norm:Ztt_sat_fp]#For a floating-point destination datatype, `sat` = 1 replaces an infinite result by the largest finite value of the same sign; with `sat` = 0 an infinite result is infinity, or the canonical NaN for a datatype without infinity.#
Overflow raises OF and NX in either case.
[#norm:Ztt_sat_nonan]#E2M1, E2M3, and E3M2 always saturate, and `sat` = 0 is reserved for them; a NaN converts to their largest positive finite value and raises NV.#
[#norm:Ztt_sat_e8m0]#For E8M0, a zero, negative, or NaN value converts to `0xff` and raises NV, and a positive value that rounds below 2^−127^ converts to 2^−127^ and raises UF and NX.#

Integer saturation is not reported: it is requested by the destination specifier and its result is intended, so a flag would add state to no purpose.

[[ztt-cc]]
==== Calling Convention

All `m` and `acc` registers are caller-saved: a called function need not preserve them, as for the vector registers and the Intel AMX tile registers.
The RISC-V psABI is the authoritative definition.
