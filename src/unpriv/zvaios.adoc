[[ext:zvaios]]
=== ext:zvaios[] Vector Extension for Atomic I/O Stores, Version 0.1

The ext:zvaios[] extension (Vector Atomic I/O Store) provides a family
of instructions that perform wide, atomic stores from vector registers
to I/O addresses. The extension enables efficient submission of
descriptors to hardware accelerators, device work queues, and other
I/O endpoints that require the entire descriptor to arrive as a
single, indivisible unit (_I/O-atomic delivery_,
<<sec:zvaios-atomicity>>). To support multi-tenant use,
hardware can insert a supervisor-controlled submission
context identifier into the store payload, so that a device shared by
mutually distrusting contexts can attribute each submission.

The extension consists of four instructions
(insn:vs128io.v[], insn:vs256io.v[], insn:vs512io.v[],
insn:vs1024io.v[]), which differ only in the width of the payload
they transfer. The first three belong to the base extension;
insn:vs1024io.v[] is provided by the ext:zvaios1024[] extension
(<<sec:zvaios-insns>>). Each instruction writes an
implementation-defined completion status word to a destination
register, or discards the status word when the destination register
is `x0`.

NOTE: This extension is in *Draft* status and has not been ratified.
The instruction encodings shown in this chapter are provisional,
pending codepoint allocation, and the CSR addresses are unassigned;
both are subject to change.

[NOTE]
====
The ext:zvaios[] extension defines a new atomicity concept
(_I/O-atomic delivery_) that extends the memory model's single-copy
atomicity guarantee to I/O targets. This concept is defined entirely
within this chapter; it remains so unless the RISC-V memory model
(RVWMO) is later extended to formalize I/O operations in general.
====

[#norm:zvaios_depends]#The ext:zvaios[] extension depends upon the
ext:zicsr[], ext:zve32x[], and ext:zvl128b[] extensions.#

Of its vector dependency, ext:zvaios[] uses only the vector register
file, the whole-register loads and stores, csr:vlenb[] and
csr:vstart[], and the `VS` context status field.

CSR access control (<<sec:zvaios-senqid>>) and the security model
(<<sec:zvaios-security>>) are described below.

[[sec:zvaios-enable]]
==== Enabling Atomic I/O Stores

A ext:zvaios[] instruction issues a wide, I/O-atomic write
(<<sec:zvaios-atomicity>>) to an I/O target from the privilege level
that executes it. The write carries a
supervisor-controlled identifier that the executing privilege level
cannot forge, so execution below M-mode is disabled until
more-privileged software enables it.

[#norm:zvaios_aiose]#Execution of a ext:zvaios[] instruction at a
privilege level below M is governed by the `AIOSE` (Atomic I/O Store
Enable) bit added to csr:menvcfg[], csr:senvcfg[], and csr:henvcfg[],
with the same control scope over lower privilege levels as the other
`envcfg` enable bits. When the `AIOSE` bit controlling the current
privilege level is clear, executing a ext:zvaios[] instruction raises
an illegal-instruction exception. When execution is in
VS-mode or VU-mode and the controlling csr:henvcfg[] bit is clear, a
virtual-instruction exception is raised instead.#

[#norm:zvaios_aiose_reset]#Each `AIOSE` bit resets to 0, so that
ext:zvaios[] instructions cannot be executed at any privilege level
below M until enabled. When the extension is implemented, ext:zvaios[]
instructions are always available in M-mode.#

[#norm:zvaios_aiose_rdonly0]#If the ext:zvaios[] extension is not
implemented, `AIOSE` is read-only zero. For implementations with the
Hypervisor extension, csr:henvcfg[] `AIOSE` is read-only zero when
csr:menvcfg[] `AIOSE` is zero.#

NOTE: The `AIOSE` bit follows the pattern of the csr:menvcfg[] enable
bits `STCE` and `CDE`: a facility usable from a lower privilege level
is disabled at reset and must be enabled through the corresponding
`envcfg` CSR. This gives privileged software a single control that can
deny a context the use of the wide-store instructions, regardless of
whether that context can access the ext:zvaios[] CSRs.

[[sec:zvaios-insns]]
==== Atomic I/O Store Instruction Family

The ext:zvaios[] extension defines four atomic I/O store instructions
that differ only in the width of the payload transferred.
[#norm:zvaios_encoding]#The instructions use the STORE-FP major opcode
(`0x27`), share a common encoding structure with existing vector store
instructions, and are distinguished from other vector stores by the
combination `mew=1`, `mop=11`, `vm=1`, and `width=111`. The 3-bit `nf`
field selects the width variant:#

[cols="^1,^2,^2,^2,^1",options="header"]
|===
| `nf[2:0]` | Mnemonic     | Bit width | Bytes | Register group

| `000`     | `vs128io.v`  | 128       | 16    | 1 register
| `001`     | `vs256io.v`  | 256       | 32    | 2 registers
| `011`     | `vs512io.v`  | 512       | 64    | 4 registers
| `111`     | `vs1024io.v` | 1024      | 128   | 8 registers
|===

The `nf` encoding follows the same `nf+1 → group size` convention
that the vector segmented store instructions use. Here, the group
size is the number of registers required to hold the full-width
payload at `VLEN >= n`, rather than the number of segments.

include::images/wavedrom/vs-n-io-v.edn[]

[NOTE]
====
The `mew=1`, `width=111` encoding space of the STORE-FP and LOAD-FP
major opcodes is shared with the tile load and store instructions of
the proposed integrated matrix extension. Those instructions use
`mop=00` and `mop=01`; ext:zvaios[] uses `mop=11`; `mop=10` is
unassigned. This grouping leaves the other `mew=1` encodings free for
a future vector extension with element widths of 128 bits and above.
If codepoint allocation moves either proposal, both assignments
should move together.
====

[#norm:zvaios_encoding_rd]#The destination register _rd_ is encoded in
bits `[24:20]` of the instruction word, in the field position that
carries `rs2` in other RISC-V store encodings. ext:zvaios[]
instructions do not consume a second source operand from this
field.#

[#norm:zvaios_store_op]#The `vs__n__io.v` instructions read the first
_n_ bits from the vector register group starting at _vs3_, insert a
supervisor-controlled submission context identifier into the payload
(<<sec:zvaios-senqid>>), perform an I/O-atomic store of
the resulting payload to the address in _rs1_, and write a completion
status word to the destination register _rd_. When _rd_ is `x0`, the
completion status word is discarded.#

[#norm:zvaios_whole_reg]#The source data is read from the vector
register file using whole-register semantics, independent of the
current values of csr:vtype[] and csr:vl[]. The number of vector
registers consumed is equal to
`max(1, n / VLEN)`. The register group must be aligned such that the
first register index is a multiple of the group size, following the
same whole-register semantics and alignment rules as the
`vs__n__r.v` whole-register store instructions of the base vector
specification.#

[#norm:zvaios_vstart]#A ext:zvaios[] instruction is reserved if
csr:vstart[] is non-zero; an illegal-instruction exception is raised
and no store is performed. A ext:zvaios[] instruction does not write
csr:vstart[]: delivery is all-or-nothing (<<sec:zvaios-atomicity>>),
so the instruction is never resumed part-way through.#

NOTE: A ext:zvaios[] instruction reads its payload with
whole-register semantics and therefore does not depend upon
csr:vtype[]. Like the whole-register loads and stores, it executes
normally when csr::[vill] is set and when csr:vtype[] has not been
configured since reset, since csr::[vill] raises an
illegal-instruction exception only for instructions that depend upon
csr:vtype[].

[#norm:zvaios_payload_init]#A ext:zvaios[] instruction transfers the
full width of the store from the vector register group regardless of
how many payload bits software has initialized. Software must
initialize every payload bit that is transferred; an uninitialized
bit carries the value that the source vector register last held.#

NOTE: Because the source is read with whole-register semantics, payload
bits that software leaves uninitialized are transmitted to the I/O
target unchanged. This includes vector-register contents left behind
by a previously-executing context. If the vector register file is
shared across security contexts and is not cleared on a context
switch, an uninitialized payload can disclose another context's data
to an external device. Software should zero or fully populate the
payload registers before issuing the store; see
<<sec:zvaios-security>>.

[#norm:zvaios_width_support]#An implementation of ext:zvaios[] must
support insn:vs128io.v[], insn:vs256io.v[], and insn:vs512io.v[].
insn:vs1024io.v[] is provided by the ext:zvaios1024[] extension,
which requires ext:zvaios[]. When ext:zvaios1024[] is not
implemented, the insn:vs1024io.v[] encoding is reserved.
<<table:zvaios-vlen>> shows the number of vector registers each
instruction occupies as a function of VLEN.#

NOTE: The 1024-bit width is separated into ext:zvaios1024[] because
its delivery path is the most expensive to implement. Its payloads
serve emerging descriptor formats: inline scatter-gather lists,
inline cryptographic IVs or keys, 128-bit addresses or
capability-carrying (CHERI-style) references, and fused
command-plus-immediate-data submissions. Implementations that serve
such devices provide ext:zvaios1024[]; others avoid the cost of a
128-byte atomic store path.

[[table:zvaios-vlen]]
.ext:zvaios[] register group size by VLEN
[cols="^1,^1,^1,^1,^1",options="header"]
|===
| VLEN | `vs128io.v` | `vs256io.v` | `vs512io.v` | `vs1024io.v`

| 128  | 1 reg       | 2 regs      | 4 regs      | 8 regs
| 256  | 1 reg       | 1 reg       | 2 regs      | 4 regs
| 512  | 1 reg       | 1 reg       | 1 reg       | 2 regs
| 1024 | 1 reg       | 1 reg       | 1 reg       | 1 reg
|===

[NOTE]
====
The payload width of each instruction is fixed by the opcode:
insn:vs256io.v[] transfers 256 bits on every implementation. Only the
number of registers that hold the payload varies with VLEN, as
`max(1, n / VLEN)`. This differs both from the whole-register store
instructions, whose register count is fixed by the opcode, and from
LMUL-scaled vector code, whose data width grows with VLEN. A
descriptor therefore has the same width and layout on every
implementation; software consults <<table:zvaios-vlen>> (or
csr:vlenb[]) only to determine how many registers to stage.
====

[#norm:zvaios_operation]#The operation of each instruction is:#
[source,text]
----
  let bytes   = n / 8
  let nregs   = max(1, bytes * 8 / VLEN)
  let data    = concat(V[vs3], V[vs3+1], ..., V[vs3+nregs-1])[0 : bytes*8-1]
  let addr    = X[rs1]
  if priv != M then {              // M-mode performs no insertion
    let length  = senqfmt.length   // vsenqfmt when V=1
    let shift   = senqfmt.shift    // vsenqfmt when V=1
    let payload = senqid[31:0]     // vsenqid  when V=1
    // Replace bits [shift+length-1 : shift] of data with payload[length-1:0]
    if length != 0 then insert_field(data, payload, shift, length)
  }
  let status  = io_atomic_store(addr, data, bytes)
  if rd != 0 then X[rd] = status
----

===== Completion Status Word

[#norm:zvaios_status_word]#A ext:zvaios[] instruction writes a
completion status word of XLEN bits to the destination register _rd_,
or discards the status word when _rd_ is `x0`. The instruction does
not retire until the status word is available in _rd_ (if captured)
and its store is committed for delivery, or until it is determined
that no payload will be delivered (<<sec:zvaios-atomicity>>).#

[#norm:zvaios_status_vocab]#The following encodings are architecturally
reserved in the status word:#

* [#norm:zvaios_status_success]#A value of 0 indicates _success_: the
  implementation has committed the store for delivery
  (<<sec:zvaios-atomicity>>) and is unable to report any condition
  that would prevent the target from processing the submission.#
* [#norm:zvaios_status_retry]#A value of 1 indicates _retry_: the
  implementation has determined that the target is temporarily unable
  to accept the submission and software should reissue the
  instruction after an implementation-defined backoff delay.#
* [#norm:zvaios_status_impl]#Values 2 and above are
  implementation-defined. An implementation must document the
  meaning of each value it produces.#

[#norm:zvaios_status_retry_nothing]#A status word of _retry_ indicates
that no byte of the payload was delivered to the target and that the
target's state is unchanged. Reissuing the
instruction after a _retry_ status therefore submits the payload
exactly once.#

[#norm:zvaios_status_impl_delivery]#An implementation that reports an
implementation-defined status value (2 or above) must document
whether the payload was delivered under that value. Software must not
reissue an instruction that reported an implementation-defined status
unless the implementation documents that value as delivering no
payload.#

NOTE: A _success_ status is not an acknowledgement by the target.
Software cannot conclude from it that the target has observed the
submission, let alone processed it. Software that needs such an
acknowledgement obtains it from the target by device-specific means.
An implementation that retires a ext:zvaios[] instruction as soon as
its store is committed for delivery, without obtaining feedback from
the target, never reports _retry_.

NOTE: The _retry_ encoding exists so that software can respond to a
full device queue without polling the device. Reissuing is safe only
if _retry_ excludes delivery: had the target accepted the payload
before _retry_ was reported, reissuing would submit it twice. The
architecture therefore binds _retry_ to non-delivery, and requires
implementations to state the delivery status of any value they define
beyond the two reserved encodings.

[#norm:zvaios_status_source]#The mechanism by which the implementation
obtains the status word is not architecturally defined. Software
must not assume that any particular bus transaction, memory
location, completion format, or interconnect protocol is involved in
producing the status word.#

[#norm:zvaios_status_binding]#The status word written to _rd_
corresponds to the specific store issued by this instruction and is
not influenced by any other outstanding store or by any other hart.#

[#norm:zvaios_status_untrusted]#The completion status word is data
produced by the implementation in response to the target and is not a
trusted value. Software must validate the status word before using it
to direct subsequent execution, and must not use it as an address,
length, or other operand without checking it. On a target shared
between security contexts, the status-word value and the timing of the
_retry_ response are potential channels; see <<sec:zvaios-security>>.#

[NOTE]
====
Deliberately leaving the source of the status word unspecified allows
implementations to choose their mechanism --- a
completion-carrying non-posted write, a response-channel code on an
on-chip interconnect, an implementation-private status path, or
status synthesized from an error-tracking structure --- without any
of these choices becoming architecturally visible to software.
Software that needs a portable indication that the submission was
accepted can rely on the architecturally-reserved encodings 0 and 1.
Software that needs device-specific information can interpret the
implementation-defined values in cooperation with the implementation
and the target device.

Software that does not need completion feedback specifies `x0` as
_rd_. The instruction then behaves as a posted "fire-and-forget"
store: the completion status word is discarded once the atomicity
guarantee is in place.

Software may still follow the common pattern of reading a
device-specific status register, at an offset from the submission
portal, after the store, using an ordinary load, with a insn:fence[]
between the store and the load if the device requires one. There is
no architectural atomicity
guarantee between the ext:zvaios[] store and a subsequent ordinary
load; drivers that require any such guarantee must rely on the
completion status word in _rd_ rather than on a follow-up load.
====

[[sec:zvaios-senqid]]
==== Submission Context Identifier

The ext:zvaios[] extension defines two families of CSRs: one holding a
supervisor-controlled submission context identifier _value_, and one
holding the supervisor-controlled _format_ describing where and how
that value is inserted into the store payload. When a ext:zvaios[]
instruction executes, the hardware reads the applicable pair of CSRs
and replaces a supervisor-specified bit range of the payload with
the supervisor-controlled identifier value before the payload is
delivered to the target.

===== Identifier Value CSRs

[#norm:zvaios_senqid]#The csr:senqid[] CSR is a supervisor-level
read-write register of XLEN bits that holds the submission context
identifier value used by ext:zvaios[] instructions executing in S-mode
or U-mode. Only the low 32 bits of csr:senqid[] are architecturally
defined; on RV64, bits [63:32] are reserved and read as zero.#

[#norm:zvaios_vsenqid]#When the Hypervisor extension is implemented,
the csr:vsenqid[] CSR is a virtual-supervisor read-write register that
shadows csr:senqid[] when `V=1`, following the shadowing mechanism
defined in <<hypervisor>>.#

[#norm:zvaios_senqid_reset]#csr:senqid[] resets to zero. The value
zero is the _null identifier_. A device that distinguishes submission
contexts by the inserted identifier should treat the null identifier
as invalid and reject the submission, so that a context whose
identifier has not been established cannot submit under a usable
identity.#

[#norm:zvaios_establish_before_run]#The csr:senqid[] CSR (and
csr:vsenqid[] under virtualization) is per-context state. Supervisor
software must establish the incoming context's identifier before that
context executes any ext:zvaios[] instruction, and must update it on
every context switch, so that a context never submits under a
previously-scheduled context's identifier.#

===== Insertion Format CSRs

[#norm:zvaios_senqfmt]#The csr:senqfmt[] CSR is a supervisor-level
read-write register that describes the insertion format used by
ext:zvaios[] instructions executing in S-mode or U-mode. It contains
two fields:#

[cols="^1,^2,^7",options="header"]
|===
| Bits    | Field    | Description

| `[5:0]`   | `length` | Number of payload bits to replace. Valid values are 0 through 32. A value of 0 selects no insertion, as defined in <<sec:zvaios-payload>>. Values 33 through 63 are reserved.
| `[15:6]`  | `shift`  | Bit offset within the store payload at which the replacement begins, counted from the least-significant bit (bit 0 of byte 0). Valid values are 0 through 1023, subject to the constraint `shift + length` &#8804; store width.
|===

[#norm:zvaios_senqfmt_res0]#Bits `[XLEN-1:16]` of csr:senqfmt[] are
reserved and read as zero.#

[#norm:zvaios_senqfmt_reset]#csr:senqfmt[] and csr:vsenqfmt[] reset to
zero, i.e. with `length` = 0, so that no insertion is performed until a
format is configured.#

[#norm:zvaios_vsenqfmt]#When the Hypervisor extension is implemented,
the csr:vsenqfmt[] CSR is a virtual-supervisor read-write register
that shadows csr:senqfmt[] when `V=1`, following the shadowing
mechanism defined in <<hypervisor>>.#

The CSR address assignments and ext:smstateen[] bit positions are to
be allocated in the privileged architecture. A summary of the
required changes is provided in <<appendix:zvaios-priv>>.

[NOTE]
====
The separation of value and format into two CSRs allows the supervisor
to manage two independent pieces of state: the identifier associated
with the current context, which changes on every context switch, and
the descriptor layout of the target device, which changes only when
the target device changes and is typically fixed for the lifetime of
a driver binding. In the common case, csr:senqfmt[] is written once
at driver initialization, and csr:senqid[] is updated on every
context switch.

The insertion position and width are configurable because descriptor
layouts differ between devices: an identifier field need not sit at
the same offset, or have the same width, in every submission format.
A fixed format would either force devices to adopt one layout or
require an instruction variant per layout. By contrast, ARM
`ACCDATA_EL1` inserts a 32-bit value at a fixed position; the
configurable format serves descriptor layouts that have not yet been
standardized. A `length` of 0 disables insertion for targets that
need none.

The 32-bit architectural width of the identifier value matches the
width of existing hardware-injected context fields in comparable
extensions, such as the 20-bit PASID field in PCIe SIOV and the
32-bit source of ARM `ACCDATA_EL1`. A single 32-bit CSR width, used
on both RV32 and RV64, accommodates both PASIDs and narrower
device-defined context identifiers.
====

===== Identifier Selection

[#norm:zvaios_id_sel]#A ext:zvaios[] instruction executing in a
privilege mode below M uses `senqid[31:0]` as the submission context
identifier value and csr:senqfmt[] as the insertion format. A
ext:zvaios[] instruction executing in M-mode performs no insertion:
its payload is delivered unmodified, as if `length` were zero.
The instruction has no operand for overriding either the identifier
value or the insertion format. Supervisor software that needs to
submit on behalf of a different context therefore saves, writes, and
restores the applicable CSRs around the submission.#

NOTE: The extension defines no machine-level identifier or format
CSRs. M-mode is the most privileged level and is trusted to construct
the entire payload, so it places any identifier that a target
requires into the payload directly, rather than relying on hardware
insertion. A machine-level insertion mechanism would add two CSRs
without any isolation benefit, since nothing constrains what M-mode
may store.

NOTE: The identifier value, the insertion format, and the enable
state that apply to a ext:zvaios[] instruction are the committed
architectural values at the instruction's program-order position. A
ext:zvaios[] store has an I/O side effect and is not performed
speculatively. An implementation that reorders execution must
therefore not deliver a submission under a stale or more-privileged
identifier around a privilege transition or a CSR write.

===== CSR Access Control

[#norm:zvaios_smstateen]#When the ext:smstateen[] extension is
implemented, a single csr:mstateen0[] bit enables access to both
csr:senqid[] and csr:senqfmt[] from privilege levels below M. When
the bit is clear, access to either CSR from the affected privilege
level raises an illegal-instruction exception. A corresponding
csr:hstateen0[] bit enables access from VS-mode when the Hypervisor
extension is implemented. The specific bit assignment is to be
allocated in <<smstateen>>.#

[#norm:zvaios_smstateen_scope]#The ext:smstateen[] bits control
explicit accesses to csr:senqid[] and csr:senqfmt[], not the implicit
reads a ext:zvaios[] instruction performs. Whether the instruction may
execute is governed by the `AIOSE` control (<<sec:zvaios-enable>>);
disabling access to the CSRs does not, by itself, prevent a context
from submitting under an established identifier.#

[[sec:zvaios-payload]]
===== Payload Insertion

[#norm:zvaios_payload_insert]#If the `length` field of the applicable
format CSR is non-zero, the hardware, before the store is issued to
the I/O system, replaces bits `[shift + length - 1 : shift]` of the
store payload with bits `[length - 1 : 0]` of the identifier value
(<<sec:zvaios-senqid>>). All other bits of the
store payload are taken unchanged from the vector register group.#

[#norm:zvaios_payload_nop]#If the `length` field of the applicable
format CSR is zero, no insertion is performed; the store payload is
delivered to the I/O system unmodified, as read from the
vector register group. The value of the `shift` field and the contents
of the identifier value CSR are ignored.#

[NOTE]
====
With `length` = 0 the executing level controls every bit of the
payload, including any bytes a device interprets as a submission
identifier. This is appropriate when the executing level is trusted to
choose the identifier (for example, M-mode, or a supervisor submitting
on its own behalf), or when the target does not use the payload
identifier for isolation. To prevent a less-privileged level from
choosing its own identifier, the owning level configures a non-zero
`length` that overwrites the identifier field; see
<<sec:zvaios-security>>.
====

[#norm:zvaios_payload_bounds]#When `length` is non-zero, the sum
`shift + length` must not exceed the width in bits of the store (128
for insn:vs128io.v[], 256 for insn:vs256io.v[], 512 for
insn:vs512io.v[], 1024 for insn:vs1024io.v[]). If the sum exceeds the
store width, an illegal-instruction exception is raised and no store
is performed.#

[#norm:zvaios_length_reserved]#If the `length` field of the applicable
format CSR holds a reserved value (33 through 63), an
illegal-instruction exception is raised and no store is performed.#

[[sec:zvaios-atomicity]]
==== Atomicity

===== Observers

[#norm:zvaios_observer_def]#An _observer_ of a ext:zvaios[] store is
any agent that can read the target address or otherwise observe its
contents. Observers include other harts, the target device itself,
and any DMA agent or other device acting on the interconnect.#

===== I/O-Atomic Delivery

[#norm:zvaios_io_atomic_def]#A ext:zvaios[] instruction performs an
_I/O-atomic store_: no observer observes the payload in a partially
complete state; each observer observes either none of it or all of
it.#

[#norm:zvaios_io_atomic_conflict]#No write by another agent to an
address that overlaps the target range is interleaved with an
I/O-atomic store. An observer observes the two writes in one order or
the other, and never a mixture of the two.#

[#norm:zvaios_io_atomic_read]#A read of the target range that is
performed concurrently with an I/O-atomic store returns either the
state before the store or the state after it, and never a mixture of
the two.#

NOTE: The two preceding rules bind the implementation and the
interconnect between the hart and the target. They cannot bind an
agent that writes the target outside that path, such as a device that
modifies its own submission portal internally.

[#norm:zvaios_io_atomic_allornothing]#Delivery is all-or-nothing with
respect to faults as well as contention. A ext:zvaios[] instruction
that raises any exception delivers no part of the payload to the
target; a partial payload is never delivered.#

[#norm:zvaios_io_atomic_mech]#The ISA does not prescribe how an
implementation achieves these guarantees. Possible mechanisms include
a wide interconnect data path, a write-combining buffer with an
atomic flush, or a dedicated I/O store path. The requirement is only
that the externally-observable behavior matches the definitions
above.#

NOTE: The definitions above are stated in terms of what an observer
can observe, rather than in terms of a bus transaction, because the
interconnect between a hart and an I/O target is not architecturally
visible.

===== Commitment for Delivery

[#norm:zvaios_commit_point]#An I/O-atomic store is _committed for
delivery_ when no subsequent action by the hart can prevent the
payload from being delivered to the target. Such actions include
raising an exception, taking an interrupt, executing a insn:fence[],
and executing any later instruction. Once the store is committed for
delivery, the payload becomes observable by the target, unless an
event occurs that would also prevent the delivery of an ordinary
posted write to the same target. Commitment does not imply that the
payload has yet been observed by the target.#

NOTE: Events that prevent the delivery of an ordinary posted write
include loss of power to the hart, the interconnect, or the target;
reset of any of these; failure of the interconnect; removal or
power-down of the target; and detection of an uncorrectable error in
the buffered payload. Congestion or backpressure at the target is not
such an event: an implementation must complete a committed delivery
however long the target takes to accept it.

[#norm:zvaios_commit_noexc]#A ext:zvaios[] instruction raises no
exception after its store is committed for delivery.#

[#norm:zvaios_io_atomic_once]#Each architectural execution of a
ext:zvaios[] instruction delivers its payload to the target at most
once. Before the store is committed for delivery, an implementation
may abandon the instruction, for example to take an interrupt, in
which case no part of the payload is delivered. After the store is
committed for delivery, the instruction retires and is not
re-executed. Re-execution of an abandoned instruction never delivers
a payload that a previous execution has already delivered.#

NOTE: These rules make a ext:zvaios[] instruction safe to interrupt.
Because the instruction does not retire until its store is committed
for delivery (<<sec:zvaios-insns>>), an implementation may hold it
pending for an extended period, during which an interrupt may preempt
it. Without an at-most-once requirement, an implementation could
issue the payload, abandon the instruction, and issue the payload
again on re-execution, delivering a non-idempotent submission twice.
An implementation that cannot withdraw a payload once issued
therefore holds the interrupt until the instruction retires.

===== Relationship to Single-Copy Atomicity

[#norm:zvaios_sca_relation]#I/O-atomic delivery extends the concept of
single-copy atomicity, defined in <<memorymodel>>, from the coherence
domain to external I/O targets. Within the coherence domain, a
ext:zvaios[] store is observed by other harts as a single-copy-atomic
store with respect to loads from the target address.#

[#norm:zvaios_single_memop]#A ext:zvaios[] instruction follows RVWMO
at the instruction level, as do other vector memory instructions.
Unlike element-wise vector stores, it gives rise to no separate
element memory operations: the payload is delivered as one
indivisible unit, as defined in this section.#

NOTE: The atomicity of a ext:zvaios[] store is defined in this
chapter rather than by reference to <<memorymodel>>, because the
target is always an I/O region (<<sec:zvaios-io>>) and the memory
model does not formalize I/O memory. Ordering with respect to other
accesses is governed by the rules for I/O writes in
<<sec:zvaios-io>>.

===== Observability

[#norm:zvaios_observability]#The atomicity guarantee applies
regardless of the interconnect topology between the hart and the
target, and to every observer, whether the target is reached via a
coherent interconnect, a non-coherent I/O interconnect, or a
combination of the two.#

[[sec:zvaios-io]]
==== I/O Classification and Ordering

[#norm:zvaios_io_only]#The target address of a
ext:zvaios[] instruction must lie in an I/O region, as classified by
the Physical Memory Attributes (<<pma>>). A ext:zvaios[] store to an
address in a main-memory region raises a store/AMO access-fault
exception, regardless of the other attributes of that region.#

[#norm:zvaios_io_writes]#ext:zvaios[] instructions are classified as
I/O writes for ordering as defined by the insn:fence[]
instruction (<<base>>). They are ordered with respect to other I/O
writes by the `PO` and `SO` predecessor and successor bits of
insn:fence[], and with respect to other memory writes according to the
`FIOM` bit in csr:menvcfg[] (<<sec:menvcfg>>) and csr:henvcfg[].#

[#norm:zvaios_pma_required]#The target address must additionally have
Physical Memory Attributes that permit I/O writes of the specified
width. If the PMAs do not permit the write, a store/AMO access-fault
exception is raised.#

NOTE: Because Physical Memory Attributes are per-region, a platform
controls where ext:zvaios[] stores are permitted by advertising or
withholding support for the corresponding write widths on each I/O
region. No new PMA is needed for this control.

[NOTE]
====
Main-memory targets are excluded deliberately. A store of up to 1024
bits to coherent main memory would have to be defined as a single
store memory operation under RVWMO, and on typical implementations
it would require single-copy atomicity across multiple cache lines.
Both are substantial obligations that lie outside the scope of this
extension. A future extension may add a
main-memory target class by defining such a store as a single memory
operation in <<memorymodel>>; nothing in this chapter prevents that
addition.
====

[[sec:zvaios-software]]
==== Software Interface

===== C Intrinsics

[#norm:zvaios_intrinsics]#A C implementation that supports the
ext:zvaios[] extension provides the following intrinsic functions,
declared in the `riscv_vector.h` header. The payload types are the
`vuint8m1_t`, `vuint8m2_t`, `vuint8m4_t`, and `vuint8m8_t` types of
the vector intrinsics specification. The intrinsic for
insn:vs1024io.v[] is provided when the ext:zvaios1024[] extension is
supported.#

[source,c]
----
unsigned long __riscv_vs128io_v_u8m1(volatile void *addr, vuint8m1_t payload);
unsigned long __riscv_vs256io_v_u8m2(volatile void *addr, vuint8m2_t payload);
unsigned long __riscv_vs512io_v_u8m4(volatile void *addr, vuint8m4_t payload);

#if defined(__riscv_zvaios1024)
unsigned long __riscv_vs1024io_v_u8m8(volatile void *addr, vuint8m8_t payload);
#endif
----

[#norm:zvaios_intrinsic_semantics]#Each call executes exactly one
corresponding instruction, with the first _n_ bits of the payload
argument as the store payload and `addr` as the target address, and
returns the XLEN-bit completion status word. A call has the ordering
semantics of a volatile access: the C implementation does not
duplicate, eliminate, or reorder it with respect to other volatile
accesses.#

[#norm:zvaios_intrinsic_discard]#When the value returned by a call is
not used, the C implementation may encode `x0` as the destination
register, discarding the status word.#

NOTE: Toolchains indicate availability with the architecture test
macros `+__riscv_zvaios+` and `+__riscv_zvaios1024+`, following the
RISC-V C API convention.

===== Usage Guidance

This section is informative.

The payload type of each intrinsic is sized for the smallest
supported VLEN of 128: it spans exactly the register group the
instruction reads at VLEN = 128, and more than the instruction reads
at larger VLEN. The instruction consumes only the first _n_ bits of
the argument, so the same source code is correct on every VLEN.

Software stages a payload with insn:vle8.v[], using an application
vector length equal to the payload size in bytes; this reads exactly
the payload from memory. The whole-register load intrinsics may be
used instead, but they transfer whole registers: a
`+__riscv_vl4re8_v_u8m4+` call reads 4 × VLENB bytes, so when VLEN
exceeds 128 the staging buffer must be readable to that size, not
merely to the payload size.

Software fully initializes every payload byte before submitting, so
that no stale register or buffer contents reach the device
(<<sec:zvaios-security>>), and validates the returned status word
before acting on it. When a payload carries secrets, such as
cryptographic keys or IVs, software should zeroize the payload
registers after submission, since their contents otherwise persist
and are saved to memory on the next context switch.

A status of 0 means the store is committed for delivery; a status of
1 means nothing was delivered and the submission may be reissued
after a backoff; any other value is implementation-defined and must
not be treated as grounds to reissue unless the implementation
documents it as delivering no payload (<<sec:zvaios-insns>>).

[source,c]
----
// Submit a 64-byte descriptor.
static inline unsigned long
submit512(volatile void *portal, const uint8_t *slot)
{
    vuint8m4_t payload = __riscv_vle8_v_u8m4(slot, 64);
    return __riscv_vs512io_v_u8m4(portal, payload);
}

int submit(volatile void *portal, const uint8_t *slot)
{
    for (unsigned tries = 0; tries <= MAX_RETRY; tries++) {
        unsigned long status = submit512(portal, slot);
        if (status == 0)
            return 0;          /* committed for delivery */
        if (status != 1)
            return -EIO;       /* implementation-defined: do not
                                  reissue unless documented safe */
        backoff(tries);        /* retry: nothing was delivered */
    }
    return -EBUSY;
}
----

Ordering with respect to other device accesses follows the rules for
I/O writes (<<sec:zvaios-io>>): a insn:fence[] with the appropriate
predecessor and successor sets is required between a submission and
any ordinary load or store to the device that must be observed in a
specific order relative to it. No fence is needed between staging a
payload and submitting it; the intrinsic consumes the payload
through a register dependency.

Execution below M-mode requires the supervisor to have set the
`AIOSE` enable (<<sec:zvaios-enable>>); a call from a context whose
enable is clear traps. The submission context identifier and its
insertion format are supervisor state (csr:senqid[], csr:senqfmt[]);
user code neither reads nor writes them.

[[sec:zvaios-security]]
==== Security Considerations

This section is informative. It states the trust model the extension
assumes and the obligations that model places on privileged software
and on the platform.

===== What insertion protects, and what it does not

The inserted identifier does not, by itself, provide isolation
between mutually distrusting domains. Like any store to an I/O
region, a ext:zvaios[] store is subject to the platform's address
translation and protection on its target address --- PMAs, PMP, and
any IOMMU --- and the extension adds no way to bypass them. Some
targets consume the inserted identifier; for example, a device may
tag its own downstream DMA with it. Even then, the platform's I/O
mediation of the hardware requester remains the boundary between
domains, exactly as it is when software writes the identifier into an
ordinary descriptor. A device must not derive a submission's
authority from the target address that the executing level chose.
Authority comes from the mediated requester; the address only selects
a submission portal.

What hardware insertion adds is a per-context identity that the
executing level cannot forge. A mediator that operates at the
granularity of hardware requesters cannot distinguish between two
U-mode processes that share a hart. csr:senqid[], written by the
supervisor and inserted by hardware, supplies that finer-grained
identity and prevents one process from submitting under another
process's identity within a single supervisor domain. This is the
property the insertion mechanism exists to provide.

===== Insertion is not a cross-domain boundary

csr:vsenqid[] is a VS-mode read-write register, so a guest may write
any value into it, and hardware inserts that value unchanged. The CPU
neither translates the value nor qualifies it with a namespace. A
device or fabric must therefore not treat the inserted identifier as
a globally-trusted identity. A platform that carries submissions
across a trust boundary must mediate the identifier with
host-controlled state: either an IOMMU keyed on the hardware
requester, or a host-programmed limit on the values a guest may
write. PASID-based I/O virtualization already meets this same
obligation by translating a guest PASID before it reaches the device.
Cross-domain isolation must not depend on the inserted identifier
alone.

===== Fail-closed enable

Execution below M-mode is disabled until privileged software sets the
`AIOSE` control (<<sec:zvaios-enable>>), which resets to 0. A
newly-reset or unconfigured hart therefore issues no submissions from
a lower privilege level. A supervisor can also withdraw the facility
from a context by clearing `AIOSE`, whether or not that context can
access the CSRs. With `length` = 0 the executing level controls the
whole payload, so the owning level must configure a non-zero
insertion for any target that relies on the identifier for isolation.
An unconfigured format (`length` = 0) does not fault. Enabling
`AIOSE` for a context and establishing its csr:senqfmt[] must
therefore be treated as a single step: a context that is enabled
while its format is still zero can supply its own identifier.

===== Software obligations

* *Context identity.* csr:senqid[] is per-context state. Supervisor
  software establishes it before entering a context that uses
  ext:zvaios[] and updates it on every context switch, so that a
  context never submits under a previously-scheduled context's
  identifier. A missed update then leaves the null identifier, which
  a conforming device rejects, rather than a usable identifier.
* *Payload contents.* The store transfers the full width from the
  vector register group, including bits that software did not
  initialize, and the vector registers are not cleared across a
  context switch. Software must fully populate the payload before
  issuing the store; otherwise it leaks a previous context's data to
  the device.
* *Completion status.* The status word in _rd_ is derived from the
  device and is untrusted; software must validate it before use.
* *Teardown.* A submission that has been committed for delivery
  (<<sec:zvaios-atomicity>>) cannot be recalled. Clearing `AIOSE`,
  changing csr:senqid[], unmapping the target, or tearing down the
  context prevents further submissions, but does not withdraw one
  already committed, which is delivered under the identifier in
  effect when it was issued. Privileged software that must ensure no
  submission remains outstanding quiesces the context before it
  reclaims the target or reassigns the identifier.

===== Availability

Each instruction emits one bus transaction of up to 1024 bits. A
lower-privilege level that is granted ext:zvaios[] can therefore
saturate a device queue or an interconnect path. A platform confines
the facility with `AIOSE`, and accounts for or rate-limits the
traffic where the facility is exposed more widely.

[[sec:zvaios-rationale]]
==== Rationale (Non-Normative)

This section is included only for the fast-track proposal. When the
extension is integrated into the final specification, it is to be
moved to the Historical Rationale appendix (<<app:rationale>>).

A descriptor wider than XLEN cannot be handed to a device in a single
store. Drivers therefore write descriptors into a memory ring and
notify the device with a doorbell store, and the device then fetches
the descriptor by DMA. Each submission costs a memory round trip, and
the ring is shared state on which producers must synchronize. The
ext:zvaios[] instructions remove both costs by delivering the whole
descriptor to the device in one atomic store.

We considered sourcing the payload from consecutive scalar registers,
as the SPARC block store did from its floating-point register file,
and from a dedicated staging buffer. On RV64, a 1024-bit payload
would occupy 16 of the 31 scalar registers, which severely constrains
register allocation; a staging buffer would add new architectural
state that must be saved and restored on every context switch. The
vector register file already provides both the state and the data
path: whole-register loads and stores are defined by the base vector
specification, and payload widths of 128 to 1024 bits arise
naturally from register grouping.

The atomic store alone is complete for a single trusted submitter;
the submission context identifier exists only so that multiple
mutually distrusting contexts can share one device. We considered
leaving the identifier entirely to software, which would simply write
it into the payload. However, an
identifier written by the executing context can be forged by that
context: an I/O mediator that operates at the granularity of hardware
requesters cannot distinguish two processes that share a hart, so one
process could submit under another's identity. Hardware insertion of
a supervisor-controlled CSR value closes this gap. The insertion
position and width are configurable through csr:senqfmt[] rather than
fixed, because descriptor layouts differ between devices, and a fixed
field would have required per-device instruction variants.

We considered making the store purely posted, with no completion
feedback. However, a device queue can be full at submission time;
without an architectural retry indication, software would have to
poll a device status register, which reintroduces the round trip the
extension removes. The completion status word in _rd_ provides the
two portable outcomes, _success_ and _retry_, at negligible cost, and
`rd = x0` preserves the posted behavior for software that does not
need feedback.

The extension is proposed on the fast track because its scope is
narrow and self-contained: it composes mechanisms that have each been
established for decades (see <<sec:zvaios-prior-art>>), modifies no
existing chapter of this manual, depends only on ext:zicsr[] and the
smallest standard vector extensions, and confines its one new concept ---
I/O-atomic delivery --- to this chapter. All external prior art
predates the 20-year horizon of the RISC-V Encumbered Information
Policy.

[[sec:zvaios-prior-art]]
==== Prior Art (Non-Normative)

This section is included only for the fast-track proposal, as review
evidence. It is to be dropped when the extension is integrated into
the final specification.

This section lists prior art supporting the mechanisms defined in the
normative sections above. All external references are at least 20
years old, consistent with the RISC-V Encumbered Information Policy.
References to other chapters of this manual are not subject to the
age cutoff.

===== Wide Atomic Delivery to Device I/O

* UltraSPARC block store (SPARC V9, 1995)
* x86 write-combining buffer flush (Pentium Pro, 1995)

_Mapping to ext:zvaios[]:_ The UltraSPARC V9 block store instructions
transferred 64 bytes between the floating-point register file and
memory as a single architectural operation, using an Address Space
Identifier to distinguish I/O from ordinary memory. The x86
write-combining buffer flush accumulates stores to a write-combining
memory region and delivers them as a single burst transaction on the
bus. Both established, by 1995, that a CPU can generate a wide,
register-sourced, indivisible write to a device address without
involving a DMA engine. ext:zvaios[] extends this established pattern
to the RISC-V vector register file and makes the atomicity guarantee
architectural rather than implementation-defined. The choice of
vector registers as the data source (rather than memory operands or
consecutive GPRs) follows the SPARC block-store precedent of reading
a wide register group as a single payload.

===== Whole-Register Vector Stores

* The `vs{1,2,4,8}r.v` whole-register store instructions defined by
  the base vector specification.

_Mapping to ext:zvaios[]:_ The ratified base vector specification's
whole-register store instructions already define the semantics of
reading a fixed number of vector registers as raw bit storage,
independent of csr:vtype[] and csr:vl[]. ext:zvaios[] inherits these
semantics directly: the ext:zvaios[] instructions read the source
vector register group using the same whole-register model, including
the register-alignment constraint and the group-size convention. The
base vector specification also establishes the `nf` field encoding
for register group sizes 1, 2, 4, and 8, which ext:zvaios[] reuses as
the width selector. Because the data path from vector register file
to the store buffer is already specified for `vs{1,2,4,8}r.v`, any
implementation of the ext:zve32x[] extension already has the
infrastructure needed for ext:zvaios[]. This removes an entire class
of potential objections to the extension: the data-movement mechanism
is not new; only the atomicity guarantee at the target and the
insertion of the submission context identifier are new.

===== Supervisor-Controlled Context Identifier Insertion

* IBM System/360 Protection Key (1964)
* Motorola MC68000 Function Codes FC0–FC2 (1979)
* SPARC Address Space Identifiers (SPARC V7, 1986)
* ARM TrustZone Non-Secure bit on AXI (AMBA3, 2003–2004)

_Mapping to ext:zvaios[]:_ The architectural pattern of a
supervisor-controlled identifier automatically attached to hardware
transactions from less-privileged code has been in continuous use
since the IBM System/360. In every listed example, the pattern is
the same: privileged software writes a value to a register, hardware
automatically uses that value to qualify subsequent operations from
less-privileged code, and unprivileged code has no path to override
the value. The System/360 Protection Key is checked against the
storage key on every memory access. The MC68000 drives function
codes FC0–FC2 on dedicated bus pins on every cycle, determined by
the processor's privilege state. SPARC V7 appends the ASI to every
memory access and restricts alternate-space instructions to
supervisor mode. The TrustZone NS bit is driven on every AXI
transaction and cannot be forged by non-secure code. The
csr:senqid[] CSR applies this same pattern to wide I/O stores: the
supervisor sets the identifier, the hardware inserts it into the
payload, and no privilege level can override it via an instruction
operand. None of this is novel architecture; it is the application of
a sixty-year-old pattern to a new destination (the I/O store payload
rather than a bus tag).

===== Configurable-Position Field Insertion During Outbound Transactions

* Burroughs B5000 tagged memory (1961)
* IBM System/38 capability tag bits (1978)
* Symbolics 3600 tagged word format (1984)
* Ethernet TCP/IP checksum offload in commercial NIC hardware (deployed by 1999)
* IEEE 802.1Q VLAN tag insertion (IEEE Std 802.1Q-1998)
* MPLS label stack push (IETF RFC 3031 and RFC 3032, 2001)
* SCSI Block Commands-2 T10 Protection Information (SBC-2, T10/1417-D, 2004)
* IEEE 802.1ad Provider Bridging (IEEE Std 802.1ad-2005)

_Mapping to ext:zvaios[]:_ The csr:senqfmt[] mechanism combines two
long-established architectural patterns. The first is
hardware-managed insertion of a metadata field into an outbound
write, which dates to tagged architectures of the early 1960s. The
Burroughs B5000 wrote architectural tag bits into every memory word
as a side effect of store execution, the IBM System/38 maintained
capability tag bits updated by the store pipeline, and the Symbolics
3600 and related Lisp machines wrote 8 bits of type tag per 36-bit
word on each store. In every case, the hardware injected an
architecturally-defined metadata field into the outbound write at a
position and width fixed by the architecture. ext:zvaios[] retains
the structural shape of these mechanisms (hardware inserts a
supervisor-controlled value into an outbound write as the write is
being issued) and parameterizes the position and width rather than
fixing them.

The second established pattern is programmable-position,
programmable-width field insertion during outbound data transmission,
which has been standard practice in networking hardware since the
mid-1990s. IEEE 802.1Q-1998 defines hardware insertion of a 32-bit
VLAN tag at a defined offset in outgoing Ethernet frames, with the
tag value drawn from a per-port or per-descriptor control register.
Commercial NICs routinely performed TCP/IP checksum offload by 1999,
computing and writing a checksum of descriptor-specified width at a
descriptor-specified offset into outgoing packets during DMA. MPLS
label push, specified in RFC 3031 and RFC 3032 in 2001, defines
hardware insertion of a variable-length label stack at a specified
position in the forwarding pipeline. The T10 Protection Information
mechanism standardized in SBC-2 in 2004 defines hardware insertion of
an 8-byte protection field at programmable intervals into write data
as it passes through a host bus adapter. IEEE 802.1ad-2005 extends
VLAN insertion to stacked tags at multiple programmable positions. In
all of these mechanisms, the hardware rewrites a specific,
software-configured bit range of an outbound transaction with a
hardware-controlled or software-configured value before the
transaction is delivered to its destination.

The csr:senqfmt[] CSR is the natural union of these two established
patterns applied to the problem ext:zvaios[] addresses. The `length`
field parameterizes the width of the inserted value, matching the
practice established by T10 Protection Information (variable length),
802.1ad (stacked variable length), and checksum offload (variable per
protocol). The `shift` field parameterizes the position of the
insertion, matching the practice established by packet-editing
engines in every programmable NIC from the mid-1990s onward. The
identifier value is drawn from a supervisor-controlled CSR, matching
the pattern established by the SPARC ASI and earlier context
mechanisms described in the preceding subsection. Each element is
old; the ext:zvaios[] contribution is the packaging of these
established elements into a single CPU instruction that binds the
rewrite to the atomic delivery of the payload to an I/O target. The
architectural novelty is the atomicity binding, not the rewrite
mechanism: a programmable-offset, programmable-width insertion of a
hardware- or supervisor-controlled value into an outbound write is
the oldest and most widely-deployed form of structured metadata
injection in general-purpose computing hardware.

===== Status Return from I/O Instructions

* IBM System/360 Start I/O (SIO) (1964)
* IBM System/370 Start Subchannel (SSCH) (System/370-XA, 1983)
* DEC PDP-11 IOT (1970)
* CDC 6600 Peripheral Processor I/O instructions (1964)

_Mapping to ext:zvaios[]:_ The pattern of an I/O-initiating
instruction that completes with a status indication delivered into
architectural register state, with the source of that status
deliberately not visible to software, is as old as I/O architecture
itself. The IBM System/360 Start I/O instruction issues a channel
program and returns a condition code in the PSW that distinguishes
successful acceptance, channel busy, subchannel busy, and not
operational, with the condition code populated from the channel's
response to the initiation request. System/370 Start Subchannel
follows the same pattern with a richer response vocabulary. The
DEC PDP-11 IOT and the CDC 6600 peripheral processor instruction
families both return condition indications derived from the
device's response to an initiated operation. In every case, the
source of the status indication --- channel logic, subchannel
machinery, peripheral processor state, or device response --- is
architecturally invisible; software sees only the resulting
condition code in register state. ext:zvaios[] adopts exactly this
pattern: the completion status word written to _rd_ is produced by
the implementation from its response to the atomic I/O store, and
the ISA does not specify where the status value originates. The
ext:zvaios[] contribution is the application of a sixty-year-old I/O
status-return pattern to a wide, register-sourced, vector-backed
atomic store rather than to a channel program.

===== CSR Allocation

New entries in the CSR allocation tables for:

* csr:senqid[], csr:vsenqid[] — identifier value registers at
  supervisor and virtual-supervisor privilege levels.
* csr:senqfmt[], csr:vsenqfmt[] — insertion format registers at the
  same two privilege levels, with the `length` and `shift` field
  layout described in <<sec:zvaios-senqid>>, resetting to zero.

CSR address assignments to be determined by the Privileged ISA editor.

===== Envcfg Enable Bit Assignment

A single new `AIOSE` bit in csr:menvcfg[], csr:senvcfg[], and
csr:henvcfg[], controlling execution of ext:zvaios[] instructions at
lower privilege levels as defined in <<sec:zvaios-enable>>. The bit
resets to 0, is read-only zero when the extension is not implemented,
and follows the read-only-zero relationship between csr:henvcfg[] and
csr:menvcfg[] used by the other `envcfg` enable bits. Bit position to
be determined by the Privileged ISA editor.

===== IOMMU and Cross-Domain Identity Mediation

Under virtualization, the identifier a guest writes to csr:vsenqid[] is
inserted verbatim and is not host-namespaced (see
<<sec:zvaios-security>>). A platform that carries ext:zvaios[]
submissions across a trust boundary must mediate the inserted
identifier with host-controlled state. It can do so either through a
host-controlled structure such as an IOMMU, keyed on the hardware
requester, or by constraining the range of values a guest may write.
The specification of this mediation is a platform and IOMMU concern
and is outside the scope of this chapter; it is noted here so that
the requirement is not lost when the extension is integrated into the
privileged architecture.

===== Smstateen Bit Assignment

A single new bit in csr:mstateen0[] controlling S-mode access to both
csr:senqid[] and csr:senqfmt[]. When the bit is clear, access from
S-mode or below to either CSR raises an illegal-instruction
exception. A single bit is used because the two CSRs are functionally
a unit: neither is useful without the other. Bit position to be
determined by the ext:smstateen[] editor.

===== Hstateen Bit Assignment

A corresponding single bit in csr:hstateen0[] controlling VS-mode
access to both csr:vsenqid[] and csr:vsenqfmt[]. When the bit is
clear, access from VS-mode or VU-mode to either CSR raises a
virtual-instruction exception. The csr:hstateen0[] bit is read-only
zero when the csr:mstateen0[] bit is zero.

===== Hypervisor Extension

Addition of csr:vsenqid[] and csr:vsenqfmt[] to the list of Virtual
Supervisor CSRs shadowed under the Hypervisor extension (<<hypervisor>>).
When `V=1`, accesses from VS-mode to csr:senqid[] and csr:senqfmt[]
are redirected to csr:vsenqid[] and csr:vsenqfmt[] respectively, using
the standard shadowing mechanism.

===== Physical Memory Attributes

No new PMA attributes are required. The existing I/O PMA attributes
are sufficient, and the restriction of ext:zvaios[] targets to I/O
regions (<<sec:zvaios-io>>) relies on the existing classification of
the address space into main-memory and I/O regions. A note may
optionally be added to <<pma>> indicating that I/O regions targeted
by ext:zvaios[] instructions must support the corresponding access
widths.

===== Memory Model

No normative changes to the memory model chapters. The I/O-atomic
delivery concept introduced in <<sec:zvaios-atomicity>> is defined
entirely within this chapter; it remains so unless RVWMO is later
extended to formalize I/O operations in general.

This holds only because ext:zvaios[] targets are restricted to I/O
regions (<<sec:zvaios-io>>), which RVWMO expressly does not
formalize. An editor who relaxes that restriction to permit
main-memory targets must reconsider this item: a store of up to 1024
bits to coherent main memory would have to be defined as a single
store memory operation under RVWMO, which changes the operation
taxonomy in <<memorymodel>> and its explanatory and formal
appendices, and which falls within the class of overlapping accesses
of differing widths that RVWMO identifies as not yet fully
understood.

===== Other Chapters

No changes to the base vector specification, the insn:fence[]
instruction description, the ext:a[] extension, or any other existing
chapter of this manual. The ext:zvaios[] chapter references these
chapters but does not modify them.
