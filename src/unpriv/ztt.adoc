[[ztt-family]]
== Ztt Family of Attached Matrix Extensions

The Ztt family of attached matrix extensions accelerates matrix multiplication and the surrounding elementwise, conversion, and reduction operations for machine-learning and high-performance computing workloads.
An attached matrix unit has its own architectural registers and executes instructions from the hart's instruction stream in program order, with precise exceptions (<<ztt-exceptions>>).
It may be decoupled from the hart; <<ztt-memory-model>> specifies how its memory accesses are ordered with those of the hart.

[#norm:Ztt_no_vstate]#The extensions do not depend on the vector extensions: they add no vector state and read none.#
Their registers are separate from the vector registers and from those of ext:zvt[] (<<ztt-zvt>>).

[#norm:Ztt_enc]#Instructions that name datatypes use the 64-bit encoding of ext:zl[]; the other instructions use 32-bit encodings in the OP-VE major opcode.#

The family consists of the base extension ext:ztt[] and extensions that add datatype combinations (<<ztt-extensions>>).
Supervisor management of Ztt contexts is specified by ext:ssttctx[] in the privileged architecture.

[NOTE]
====
Datatypes are a property of the instruction, not of the registers: every instruction names the datatypes of its operands, and the registers are untyped containers.
An instruction therefore depends on no configuration state, its legality and the registers it accesses are known when it is decoded, and a compiler, disassembler, or debugger reads its semantics from the instruction alone.
The tile side _N_ is the only implementation parameter visible to software; like VLEN, it scales loop bounds and strides, but not register numbers or data layouts.
====

[[ztt-params]]
=== Implementation-defined Constant Parameters

[#norm:Ztt_N]#Each hart that implements a Ztt extension defines one parameter, the tile side _N_, which must be a multiple of 4.#
// OPEN (decision 17): the minimum N.

_N_ sets the number of elements a register holds and the inner dimension of a matrix multiply.
It does not change which registers an operand occupies.

NOTE: A row of packed 6-bit elements (four in three bytes) or of 2-bit elements (four per byte) is a whole number of bytes only when _N_ is a multiple of 4.

Ztt supports binary code that executes on harts with different values of _N_, provided the harts support the datatypes and instructions it uses.

NOTE: Thread contexts with live Ztt state cannot be migrated between harts with different values of _N_.

[[ztt-model]]
=== Attached Matrix Programmer's Model

[#norm:Ztt_state]#Ztt adds to each hart 32 matrix registers, `m0` to `m31`, _R_ accumulator registers, `acc0` to ``acc``__R__``−1``, and the read-only CSR csr:amenlenb[].#
A matrix multiply reads its operands from matrix registers and accumulates into an accumulator register; the other operations read and write matrix registers.

NOTE: The state is architecturally per hart, but a matrix unit may hold several contexts: one context for one hart, several contexts for one hart, such as for an interactive and a real-time task, or contexts for several harts.
Harts that share a unit have the same _N_.
A context is only register contents, as no configuration state exists (<<ztt-datatypes>>); only loads and stores raise exceptions other than illegal-instruction exceptions, which are decided at decode (<<ztt-exceptions>>); a unit may access memory through its own path (<<ztt-memory-model>>); and register images do not depend on internal storage (<<ztt-register-images>>).
A context can thus move between units, and software sees the configuration only through performance.
<<ext:ssttctx>> specifies how contexts are bound to harts.

[[ztt-mregs]]
==== Matrix Registers

[#norm:Ztt_mreg]#Each matrix register holds _N_ {times} _N_ 16-bit elements.#
<<ztt-operands>> describes how operands of other widths occupy matrix registers.

[[ztt-accregs]]
==== Accumulator Registers

[#norm:Ztt_accreg]#Each accumulator register holds _N_ {times} _N_ 32-bit elements.#
[#norm:Ztt_R]#There are _R_ = 8 accumulator registers.#

NOTE: Attention keeps its output, _d_/__N__ accumulators for a head dimension _d_, in accumulators across all blocks of keys.
Flash attention (<<ztt-example-flash>>) needs one more for the scores, one for their row sums, and another to compute the next block's scores while the current one completes, so eight accumulators hold an output of _d_ = 5__N__, or of _d_ = 6__N__ without the overlap.
An attention that stores its scores in memory (<<ztt-example-attn-2p>>) holds nothing else in the pass that computes the output, so eight accumulators hold an output of _d_ = 8__N__, a head dimension of 128 at _N_ = 16.
Fewer accumulators would slice the common head dimensions of 64 and 128 at small _N_, while more would add state to every context and every context switch without benefit to the other kernels, which a 2 {times} 4 block of a matrix multiply already serves.

[[ztt-discard]]
==== Context Discard

[#norm:Ztt_mdiscard]#The insn:mdiscard[] instruction raises an illegal-instruction exception if csr:mstatus[ts] is Off, or, when V=1, if csr:vsstatus[ts] is Off.
Otherwise, it sets csr:mstatus[ts] to Initial, and, when V=1, csr:vsstatus[ts].#
[#norm:Ztt_mdiscard_state]#After insn:mdiscard[], the contents of all `m` and `acc` registers are UNSPECIFIED.#

NOTE: insn:mdiscard[] need not write the registers.
Software executes it where its use of Ztt state ends, so that the state is not saved on a context switch and an implementation can reclaim its storage.

[[ztt-amenlenb]]
==== Matrix Row Byte Length (csr:amenlenb[]) Register

[#norm:Ztt_amenlenb]#The _XLEN_-bit-wide read-only CSR csr:amenlenb[] holds 2__N__, the length in bytes of a row of a matrix register.#
// OPEN: CSR address, in the unprivileged read-only range next to vlenb.

NOTE: The value in csr:amenlenb[] is a design-time constant in any implementation.

NOTE: Software uses the row length in bytes to step addresses and to scale leading dimensions, without converting from _N_.

[[ztt-fcsr]]
==== Floating-Point Exception Flags and Rounding Mode

[#norm:Ztt_fflags]#Floating-point exceptions raised by Ztt instructions accrue in csr:fflags[], and the DYN rounding mode is that in csr:frm[].#
Ztt has no exception-flag or rounding-mode state of its own.

[#norm:Ztt_fs]#For the purposes of csr:mstatus[fs] and csr:vsstatus[fs], a Ztt instruction that names a floating-point datatype is a floating-point instruction that writes csr:fflags[].#
// OPEN: dependency of the floating-point datatypes on F or Zfinx (cf. Zve32f).

NOTE: A matrix unit that completes Ztt instructions after the hart has retired them can merge their flags into csr:fflags[] late and in any order, because accrued flags never trap.
Only accesses to csr:fflags[] and csr:fcsr[] must be ordered with older Ztt instructions: a read must observe their flags, and a write must not be overtaken by them, which an implementation may ensure by waiting for them to complete.
csr:frm[] can be read when an instruction issues.
Decoupled vector implementations face the same requirement.

[[ztt-zvt]]
==== Coexistence with Zvt

[#norm:Ztt_Zvt_disjoint]#Ztt state and Zvt tile state are disjoint: no Ztt instruction reads or writes Zvt tile state, and no Zvt instruction reads or writes Ztt state.#
Each has its own context-status field.

NOTE: An implementation may share physical storage between the two, but must preserve both while both are live, for example by spilling one.
A context status of Initial indicates that the corresponding state need not be preserved.

[[ztt-type-codes]]
==== Type Codes

Datatypes are named by 5-bit type codes.
For integer datatypes, bit 4 is 0, bits 3:1 are log~2~ of the width minus 1, and bit 0 is set for unsigned datatypes.
Floating-point type codes have bit 4 set and are enumerated.

[[ztt-specifiers]]
==== Operand Specifiers

The datatypes of an instruction's operands are given by operand specifiers:

[%autowidth,float="center",align="center",cols="<,<,>",options="header"]
|===
|Specifier |Fields |Width
|Destination |type code, rounding mode `rm`, saturation `sat` |9 bits
|Source |type code |5 bits
|===

<<ztt-encoding-64>> gives their positions in the encoding.
In assembly, a datatype follows its register name, separated by a dot, as in `acc2.fp32`; the rounding mode and `sat`, when given, are trailing operands, as in F, and an omitted rounding mode is DYN for floating-point datatypes.
A matrix-register operand that occupies a group of _G_ registers is written with the suffix ``x``__G__, as in `m4x2.int8`, also where the datatype requires the group, as in `m12x2.fp32`; an operand in one register has no suffix.
An assembler rejects operands whose numbers of columns differ (<<ztt-enc-columns>>).
[#norm:Ztt_spec_rsv]#A specifier field value that the operation does not use, or that is reserved for the named datatype, raises an illegal-instruction exception.#

==== Rounding Modes

[#norm:Ztt_rm]#The `rm` field selects how a result that is not exactly representable in the destination datatype is rounded.
It takes the integer encodings when the source and destination datatypes are all integer datatypes, and the floating-point encodings otherwise.#

[[ztt-rm-table]]
.Rounding mode encoding.
[%autowidth,float="center",align="center",cols="^,<,<",options="header"]
|===
|`rm` |Floating-point encodings |Integer encodings
|000 |RNE |RNU
|001 |RTZ |RNE

[#norm:Ztt_rm_int_ext]#The integer encodings RMM, RTZ, and RUP round to nearest with ties away from zero, toward zero, and toward +{inf}, respectively.#

NOTE: Integer RMM is the rounding of the requantization in common inference libraries, so a right shift by insn:mldexp[] can match them exactly.
[#norm:Ztt_rm_dyn]#DYN selects the rounding mode in csr:frm[]; as in F, the behavior when csr:frm[] holds a reserved value is reserved.#
[#norm:Ztt_rm_rod_int]#The floating-point encoding ROD is reserved when the destination datatype is an integer datatype.#

[[ztt-saturation]]
==== Saturation

[#norm:Ztt_sat_int]#For an integer destination datatype, `sat` = 1 clamps a result that is out of range to the nearest representable value, and `sat` = 0 wraps it modulo 2^_n_^.#
[#norm:Ztt_sat_fp2int]#A conversion from a floating-point to an integer datatype always saturates as in F, and raises NV when the source is NaN or out of range; `sat` = 0 is reserved for it.#

[#norm:Ztt_sat_fp]#For a floating-point destination datatype, `sat` = 1 replaces an infinite result by the largest finite value of the same sign; with `sat` = 0 an infinite result is infinity, or the canonical NaN for a datatype without infinity.#
Overflow raises OF and NX in either case.
[#norm:Ztt_sat_nonan]#E2M1, E2M3, and E3M2 always saturate, and `sat` = 0 is reserved for them; a NaN converts to their largest positive finite value and raises NV.#
[#norm:Ztt_sat_e8m0]#For E8M0, a zero, negative, or NaN value converts to `0xff` and raises NV, and a positive value that rounds below 2^−127^ converts to 2^−127^ and raises UF and NX.#

Integer saturation is not reported: it is requested by the destination specifier and its result is intended, so a flag would add state to no purpose.

[[ztt-mreg-layout]]
==== Matrix Registers

[#norm:Ztt_mreg_rows]#A matrix register holds _N_ rows of 2__N__ bytes.#
[#norm:Ztt_mreg_operand]#An operand of element width _w_ held in one matrix register is an _N_ {times} 16__N__/__w__ matrix in row-major order: element (_r_, _c_) occupies bits _w_ {times} _c_ + _w_ − 1 to _w_ {times} _c_ of row _r_, numbering the bits of a row from bit 0 of its first byte.#
The element width of each datatype is given in <<ztt-type-code-table>>.

[[ztt-groups]]
==== Register Groups

[#norm:Ztt_group]#An operand may occupy a group of _G_ = 2 or 4 consecutive matrix registers, the first of which has a register number that is a multiple of _G_.
Register _j_ of the group holds columns _j_{nbsp}{times}{nbsp}16__N__/__w__ to (__j__ + 1){nbsp}{times}{nbsp}16__N__/__w__ − 1, so the operand is an _N_ {times} 16__GN__/__w__ matrix.#
[#norm:Ztt_group_size]#An _N_ {times} _N_ matrix operand of element width _w_ > 16 occupies _G_ = _w_/16 registers.
A matrix multiply may use a larger _G_ for its wider source (<<ztt-ops>>).
Elementwise operations on matrix registers take no groups (<<ztt-ops-elementwise>>).
No operand occupies more than four registers.#
[#norm:Ztt_group_align]#An instruction that names a group whose first register number is not a multiple of _G_ raises an illegal-instruction exception.#

[NOTE]
====
Groups are used only where an operand's shape must match another operand's:

* the sources of a matrix multiply, which hold _K_ columns each, so that _K_ grows with the group and a narrower source occupies a smaller group;
* conversions between matrix registers of different element widths, which keep the number of columns;
* an _N_ {times} _N_ matrix of a datatype wider than 16 bits that is combined with an accumulator register;
* index matrices (<<ztt-ops-const>>), whose values follow the operand's shape;
* loads and stores, which transfer several registers with one instruction.

An elementwise operation pairs corresponding elements whatever the shape, so it operates on single registers.
This bounds the matrix registers an instruction accesses: at most three for an elementwise operation, and at most eight for any other instruction.
====

[[ztt-acc-layout]]
==== Accumulator Registers

[#norm:Ztt_acc_layout]#An accumulator register holds an _N_ {times} _N_ matrix of 32-bit elements in row-major order.#
[#norm:Ztt_acc_narrow]#A value of an accumulator datatype narrower than 32 bits occupies the low bits of its element; the other bits are written as zero and ignored when read.#

Matrix multiplies read and write only accumulator datatypes of 32 and 64 bits; the narrower ones are produced by insn:mcvt[] and transferred by the accumulator loads and stores.

[#norm:Ztt_acc_pair]#An accumulator of a 64-bit datatype occupies an _accumulator pair_, two consecutive accumulator registers of which the first has an even register number, and holds an _N_ {times} _N_ matrix of 64-bit elements.
The even register holds columns 0 to _N_/2 − 1, and the odd register columns _N_/2 to _N_ − 1.
In each register, 64-bit element (_r_, _c_) of its _N_ {times} _N_/2 matrix occupies 32-bit elements (_r_, 2__c__), which holds the low half, and (_r_, 2__c__ + 1).#
[#norm:Ztt_acc_pair_align]#An instruction that names an accumulator pair whose first register number is odd raises an illegal-instruction exception.#
In assembly, a pair is named by its first register, as in `acc2.fp64`.

Only the 64-bit accumulation extensions (<<ztt-ext-acc64>>) define 64-bit accumulator datatypes.

[[ztt-register-images]]
==== Whole-Register Images

[#norm:Ztt_mreg_image]#The image of a matrix register is its 2__N__^2^ bytes, row 0 first.#
[#norm:Ztt_acc_image]#The image of an accumulator register is its _N_^2^ 32-bit elements in row-major order, each in little-endian byte order.#
[#norm:Ztt_image_arch]#Images are independent of how an implementation stores registers internally; whole-register loads and stores transfer them unchanged.#

The image of each register of an accumulator pair is therefore its _N_ {times} _N_/2 64-bit elements in row-major order, each in little-endian byte order.

NOTE: The images are architectural so that debuggers, and contexts migrated between harts with the same _N_, observe the same bytes on every implementation.

[[ztt-enc-columns]]
==== Operand Columns

[#norm:Ztt_cols_same]#All matrix-register operands of an instruction have the same number of columns, _C_.#
[#norm:Ztt_cols_kc]#Matrix multiplies and conversions encode _C_ = 2^`kc`^{nbsp}{times}{nbsp}__N__ in a 3-bit field `kc`; the values 6 and 7 are reserved.
An operand of element width _w_ then occupies _G_ = 2^`kc`^{nbsp}{times}{nbsp}__w__/16 registers.#
[#norm:Ztt_cols_g]#An operand with _G_ < 1 is a slot of a register (<<ztt-mreg-layout>>), and is valid only where _C_ = _N_ and the instruction encodes a slot index.
An instruction for which an operand's _G_ is otherwise less than 1, is greater than 4, or is not valid for its datatype (<<ztt-groups>>) raises an illegal-instruction exception.#

_G_ does not depend on _N_, so the registers an instruction accesses follow from its register fields, `kc`, and the element widths of its datatypes.
The column field applies to the instruction groups as follows:

[%autowidth,float="center",align="center",cols="<,<",options="header"]
|===
|Instructions |Column field
|Matrix multiplies |_C_ is _K_; each source occupies the group that holds _K_ columns of its datatype.
|Elementwise operations, compares, and bitwise operations on matrix registers |Each operand is one register; no column field.
|Conversions |_C_ as encoded, and _N_ when an operand is an accumulator register; with _C_ = _N_, an operand narrower than 16 bits is a slot.
|Other operations with an accumulator operand |_C_ is _N_, the columns of an accumulator; an operand narrower than 16 bits is a slot. No column field.
|Loads and stores |A single matrix-register operand: the 32-bit forms encode its group size _G_ directly, as log~2~ _G_ in 2 bits.
|===

[#norm:Ztt_cols_mixed]#In a matrix multiply whose sources differ in element width, both hold _K_ columns, so the narrower source occupies the smaller group.#
For example, with the mixed-width extension:

[source,asm]
----
mmacc    acc0.int32, m0.int4, m2x2.int8      # K = 4N, kc = 2
mmacc    acc1.int32, m4.int2, m8x4.int8      # K = 8N, kc = 3
----

An INT2 source in one register holds 8__N__ columns, so its INT8 partner occupies four registers.
A ratio of element widths greater than four is not encodable, because the wider source would occupy more than four registers.

NOTE: One field serves instructions with any number of matrix-register operands.
Encoding the group size of each operand separately would express the same set of instructions, with more bits and with encodings whose operands differ in their numbers of columns.

[[ztt-memory]]
=== Matrix Loads and Stores

Ztt loads and stores transfer a matrix register, a register group, or an accumulator register between memory and the hart.
The whole-register forms transfer the register image; the other forms transfer the operand matrix (<<ztt-operands>>) row by row.
Their encodings are 32-bit (<<ztt-encoding-32>>), except for the partial-tile forms, which use the 64-bit format (<<ztt-encoding-64>>).

[[ztt-memory-encoding]]
==== Element Sizes

[#norm:Ztt_ls_esize]#Each load and store other than the whole-register forms carries its element size in its encoding.#

[[ztt-esize-table]]
.Load and store element sizes.
[%autowidth,float="center",align="center",cols="<,<,^,^",options="header"]
|===
|Suffix |Element size |Matrix registers |Accumulator registers
|`e2` |2 bits |yes |no
|`e4` |4 bits |yes |yes
|`p6` |6 bits, packed |yes |no
|`e8` |8 bits |yes |yes
|`e16` |16 bits |yes |yes
|`e32` |32 bits |yes |yes
|`e64` |64 bits |yes |pairs only
|===

[#norm:Ztt_ls_p6]#`p6` transfers 6-bit elements stored four in three bytes in memory, element _k_ of a row occupying bits 6__k__ + 5 to 6__k__ of the row, numbering the bits of a row from bit 0 of its first byte; in a matrix register each element occupies an 8-bit container as in <<ztt-fp-formats>>.#
[#norm:Ztt_ls_esize_reg]#The element size determines the shape of the operand matrix and the size of the register group, as for an operand of that element width.#

[[ztt-memory-addressing]]
==== Strided and Transposing Forms

[#norm:Ztt_ls_addr]#These forms take the base address in `rs1` and the leading dimension _LD_, in elements, in `rs2`.
They view memory as a matrix whose element (_d_, _k_) is at bit offset (_d_{nbsp}{times}{nbsp}__LD__ + _k_) {times} _w_ from the base address, where _w_ is the element size; address arithmetic is modulo 2^XLEN^.#

NOTE: For elements narrower than 8 bits, a strided load or store that transfers whole rows moves the same bits as its `e8` form with _LD_ {times} _w_ / 8 as the leading dimension.

In assembly, these forms are written with the leading dimension last, as in `mls.st.e16 m0, (a0), a1`.
For the matrix-register loads, a leading dimension of `x0` may be omitted, as in `mls.st.e32 m4x2, (a7)`.

NOTE: With _LD_ = 0, every row is read from the same memory row, so a load replicates a vector, such as a bias, into every row of the register.

[#norm:Ztt_ls_forms]#For an operand matrix element (_r_, _c_):#

* [#norm:Ztt_ls_st]#The strided forms, insn:mls.st[] and insn:mss.st[], transfer memory element (_r_, _c_).#
* [#norm:Ztt_ls_tst]#The transposing forms, insn:mls.tst[] and insn:mss.tst[], transfer memory element (_c_, _r_).
They are reserved for the element size `p6`.#

[#norm:Ztt_ls_acc]#The accumulator forms, insn:mla.st[], insn:msa.st[], insn:mla.tst[], and insn:msa.tst[], transfer an accumulator register as the strided and transposing forms do, with element sizes of 4, 8, 16, and 32 bits.
A load of a narrower element size writes the low bits of each 32-bit element and zeroes the others; a store writes the low bits.#
[#norm:Ztt_ls_acc64]#With element size `e64`, the accumulator forms transfer an accumulator pair as an _N_ {times} _N_ matrix of 64-bit elements.
They are reserved unless a 64-bit accumulation extension (<<ztt-ext-acc64>>) is implemented.#

NOTE: A row-major matrix and the transpose of a column-major matrix load with the strided form.

NOTE: In a transposing load of elements narrower than 8 bits, each byte of memory row _c_ holds element _c_ of 8/__w__ consecutive register rows.
An implementation transposes bytes, as for 8-bit elements, and distributes the _w_-bit fields of each byte to their rows by a fixed rearrangement; a transposing store reverses both steps.
A row-major B of 2-, 4-, or 8-bit elements thus loads as B^T^ for insn:mmacc[], while a B of 6-bit elements is packed in advance.

[[ztt-memory-partial]]
==== Partial-Tile Forms

[#norm:Ztt_ls_partial]#Each strided, transposing, and accumulator form has a partial-tile variant that also takes a row count and a column count from X registers.
It transfers only the elements whose row index is below the row count and whose column index is below the column count; a count at least the number of rows or columns of the operand matrix selects all of them.#
[#norm:Ztt_ls_partial_load]#A partial-tile load writes zero to the elements it does not transfer.#
[#norm:Ztt_ls_partial_store]#A partial-tile store does not access memory for the elements it does not transfer.#

NOTE: A partial-tile load pads an edge tile, or a short inner dimension, without a separate clearing step: if both sources of a matrix multiply are loaded with the same column count, the zero-filled columns contribute only +0 products.
The counts also tell an implementation which elements are zero; the product of a zero element needs no significand multiply, only its sign and the handling of an infinite or NaN partner (<<ztt-matmul-numerics>>).

[[ztt-memory-whole]]
==== Whole-Register Forms

[#norm:Ztt_ls_whole]#insn:mls.1r[] and insn:mss.1r[] transfer the image of one matrix register, 2__N__^2^ bytes, between the register and consecutive bytes starting at the address in `rs1`.
insn:mla.1r[] and insn:msa.1r[] do the same for the image of an accumulator register, 4__N__^2^ bytes.#

[[ztt-memory-alignment]]
=== Matrix Memory Alignment Constraints

[#norm:Ztt_ls_align]#Each element of 8 bits or more accessed by a Ztt load or store must be naturally aligned to its size.
For smaller elements, each row must begin at a byte boundary, so _LD_ {times} _w_ must be a multiple of 8.
Otherwise, the instruction raises an address-misaligned exception.#
[#norm:Ztt_ls_align_whole]#The whole-register forms have no alignment requirement beyond bytes.#

[[ztt-memory-model]]
=== Matrix Memory Consistency Model

The memory operations of a hart form two streams: the _Ztt stream_, made of the memory operations of Ztt instructions, and the _hart stream_, made of all its other memory operations, including vector loads and stores, AMOs, LR/SC, and cache-management operations.

[#norm:Ztt_mm_within]#Within the Ztt stream, memory operations are ordered as by RVWMO at the instruction level, and, if the ext:ztso[] extension is implemented, by RVTSO at the instruction level.#
[#norm:Ztt_ls_unordered]#Element accesses are unordered within an instruction.#
[#norm:Ztt_ls_partial_ctrl]#Partial-tile forms have a control dependency on their row and column counts, rather than a data dependency.#

[#norm:Ztt_mm_across]#A memory operation in one stream is ordered before a memory operation of the same hart in the other stream only if a FENCE instruction orders them, an acquire or release annotation orders them, or a syntactic dependency orders them, under the rules of RVWMO.
Program order alone, even to overlapping addresses, does not order them, including when the ext:ztso[] extension is implemented.#
[#norm:Ztt_mm_fence]#FENCE and FENCE.TSO apply their predecessor and successor sets to Ztt memory operations as to any other memory operation of the hart; a Ztt memory operation is a device input or output operation, or a memory read or write, according to the PMAs of the location it accesses.#
[#norm:Ztt_mm_sfence]#SFENCE.VMA orders the implicit accesses for address translation made by Ztt memory operations as it does those of other memory operations.#
[#norm:Ztt_mm_shared]#The memory operations that a matrix unit shared by several harts performs for a Ztt instruction belong to the Ztt stream of the hart that executed it.#

[NOTE]
====
The two streams let a matrix unit access memory through its own path, like an agent separate from the hart, while FENCE instructions and synchronization idioms keep working unchanged.
Data passed between the streams within a hart needs a fence:

* a store in the hart stream read by a Ztt load: `fence w,r`;
* a Ztt store read by a load in the hart stream: `fence w,r`;
* a load in one stream followed by an overlapping store in the other: `fence r,w`;
* overlapping stores in the two streams that must take effect in program order: `fence w,w`.

A release annotation, such as on `amoswap.w.rl`, also orders older Ztt memory operations, so a lock release needs no additional fence.
Taking a trap and executing an xRET instruction do not order the streams, so a handler that fills or copies a page for a faulting Ztt load or store executes a fence before the instruction is retried.
====

[[ztt-matmul-numerics]]
==== Matrix-Multiply Numerics

A floating-point matrix multiply updates element (_i_, _j_) of C with the _K_ products of element (_i_, _k_) of A and element (_j_, _k_) of B.

[#norm:Ztt_num_sdp]#Consecutive products form sub-dot-products of _W_ products, where _W_ is 16 divided by the larger source element width, or 1 when that width is 16 bits or more.#
[#norm:Ztt_num_steps]#Consecutive sub-dot-products form steps of _N_ sub-dot-products.
The result is that of applying the steps one at a time, in increasing order of _k_.#

[#norm:Ztt_num_group]#Within a step, the sub-dot-products are partitioned into consecutive groups of _P_, where _P_ is an implementation-defined power of two that divides _N_.
Each group is reduced to a partial sum _S_ according to an implementation-defined parameter `psm`:#

* [#norm:Ztt_num_psm0]#If `psm` = 0, _S_ is exact.#
* [#norm:Ztt_num_psm1]#If `psm` = 1, _S_ is formed by an implementation-defined non-exact reduction of the group's products.
The implementation discloses the algorithm and the values of its parameters.#

[#norm:Ztt_num_rnd]#Before it is accumulated, _S_ is treated according to an implementation-defined parameter `rnd`:#

* [#norm:Ztt_num_rnd_rm]#If `rnd` = `rm`, _S_ is rounded to the datatype of C as selected by `rm`.#
* [#norm:Ztt_num_rnd_rto]#If `rnd` = `rto`, _S_ is rounded to the datatype of C with round to odd.#
* [#norm:Ztt_num_rnd_xct]#If `rnd` = `xct`, _S_ is not rounded.#

[#norm:Ztt_num_acc]#Each group then updates the element as C~__i__,__j__~ {leftarrow} round~rm~(C~__i__,__j__~ + _S_), rounding as selected by `rm`.#

[#norm:Ztt_num_disclose]#An implementation discloses its (_P_, `psm`, `rnd`) for each combination of source element widths and C datatype that it supports.
The disclosed values apply to every datatype combination with those widths.#

[#norm:Ztt_num_special]#Special values are handled as if each product were exact and each sum and rounding of the model were the corresponding IEEE 754 operation: an invalid product or sum, or a NaN source, produces the canonical NaN.#
[#norm:Ztt_num_flags]#The flags accrued in csr:fflags[] are the bitwise OR of the flags raised by the operations of the model, in any order.#

NOTE: _P_, `psm`, and `rnd` are the parameters `G`, `psm`, and `rnd` of the floating-point matrix multiplies of ext:zvvmm[], with `rm` in place of `frm`, so the same disclosure describes both.

[[ztt-exceptions]]
=== Exception Handling

[#norm:Ztt_exc_precise]#Ztt instructions raise exceptions precisely: when an exception is taken on a Ztt instruction, all older instructions have completed, and no younger instruction has changed architectural state.#
[#norm:Ztt_exc_decode]#Apart from exceptions raised in fetching them and breakpoints, Ztt instructions other than loads and stores raise no exceptions other than illegal-instruction exceptions, which depend only on the instruction, on csr:mstatus[ts], csr:vsstatus[ts], and csr:frm[], and on XLEN.#

NOTE: An implementation can therefore decide at decode whether such an instruction raises an exception, and dispatch it to a matrix unit without waiting for its completion.

[#norm:Ztt_exc_ls_restart]#A Ztt load or store that raises an exception is restarted from its beginning when it is resumed.
A load that raises an exception leaves its destination registers unchanged; a store that raises an exception may have written any part of its data to memory.#

NOTE: Ztt has no counterpart to csr:vstart[].
Restarting a store rewrites the elements written before the exception with the same values.

[[ztt-ops-mmacc]]
==== Matrix Multiply

[#norm:Ztt_mmacc]#insn:mmacc[] computes C {leftarrow} C + A {times} B^T^, where C is an accumulator register and A and B are matrix-register operands.#
Transposing loads supply A^T^ and B^T^ (<<ztt-memory-addressing>>).

[#norm:Ztt_mmacc_shape]#A and B are the _N_ {times} _K_ matrices held by their operands (<<ztt-groups>>).#
[#norm:Ztt_mmacc_k]#The two source operands have the same number of columns, _K_ (<<ztt-enc-columns>>).#

[NOTE]
====
Ztt has a single matrix-multiply form, as ext:zvvmm[] has, which reads both sources along _K_, by rows:

* A transposing load of B and insn:mmacc[] give the result of a form that multiplies by B, because the numerics depend only on _k_ (<<ztt-matmul-numerics>>).
* A form that multiplies by B reads B by columns, which an implementation that reads both sources by rows executes at a fraction of the rate or with an added transpose unit, so kernels would be tuned to each implementation.
* Kernels, packing routines, and compilers carry over between ext:zvvmm[] and Ztt.
====

[#norm:Ztt_mmacc_spec]#The destination specifier names the datatype of C, which is both read and written; the source specifiers name the datatypes of A and B.#
Widening is expressed by these datatypes alone:

[source,asm]
----
mmacc    acc2.fp32, m0.e4m3, m4.e5m2          # FP8 into FP32, rounding mode DYN
mmacc    acc1.int32, m0x2.uint8, m2x2.int8    # K = 4N
mmacc    acc0.fp32, m0.bf16, m8.bf16, rne    # rounding mode RNE
----

[#norm:Ztt_mmacc_combos]#Ztt supports the datatype combinations of <<ztt-mmacc-table>>, in which A and B have the same element width and may otherwise differ.
Other combinations raise an illegal-instruction exception unless an extension supports them.#

[[ztt-ops-elementwise]]
==== Elementwise Operations

[#norm:Ztt_ew_operands]#An elementwise operation applies to corresponding elements of matrix-register operands of one element width, each of which is one matrix register, or of accumulator registers as listed in <<ztt-acc-ops-table>>.
A scalar operand, taken from an X register or from a 7-bit signed immediate in the instruction, applies to every element.#
[#norm:Ztt_ew_scalar]#An X register supplies the encoding of a value of _w_ bits in its low _w_ bits; _w_ > XLEN is reserved.
An immediate is a signed integer and is reserved for an operand of a floating-point datatype.#

NOTE: Elementwise operations take no register groups (<<ztt-groups>>), so an _N_ {times} _N_ matrix of a 32-bit or 64-bit datatype in matrix registers takes two or four instructions.

[[ztt-ops-arith]]
===== Arithmetic

[#norm:Ztt_ew_arith]#insn:madd[], insn:msub[], and insn:mmul[] compute _a_ + _b_, _a_ − _b_, and _a_ {times} _b_ of corresponding elements _a_ of the first and _b_ of the second source.
For a floating-point datatype, the result is rounded as selected by `rm` and saturated as selected by `sat`.
For an integer datatype, the result wraps or saturates as selected by `sat`, and an `rm` other than 0 is reserved.#
[#norm:Ztt_ew_minmax]#insn:mmax[] and insn:mmin[] write the larger and the smaller of _a_ and _b_.
For floating-point datatypes they are the maximumNumber and minimumNumber operations of IEEE 754-2019, as insn:fmax.s[] and insn:fmin.s[].
An `rm` other than 0 and `sat` are reserved for them.#
[#norm:Ztt_ew_msmul]#insn:msmul[] is a fixed-point multiply for signed integer datatypes of width _w_: it shifts _a_ {times} _b_ right by _w_ − 1, rounding as selected by `rm`, and saturates the result; `sat` = 0 is reserved.#

NOTE: insn:msmul[] is the fractional multiply of the vector extension's insn:vsmul.vv[], and the scaling step of integer requantization.

[#norm:Ztt_ew_types]#The arithmetic operations support every integer datatype and every floating-point datatype except E8M0 and TF32; insn:msmul[] supports only signed integer datatypes.
The source and destination datatypes are equal.#

[[ztt-ops-mldexp]]
===== Power-of-Two Scaling

[#norm:Ztt_mldexp]#insn:mldexp[] (matrix load exponent) computes each element of its destination as the corresponding element of its source multiplied by 2^__e__^, where the exponent _e_ is the corresponding element of a third operand of the signed integer datatype of the source's width, or a scalar or broadcast operand.
The source and destination datatypes are equal.#

[#norm:Ztt_mldexp_mod]#With the flag `mod` set, the exponent is reduced modulo the element width; `mod` is reserved for floating-point datatypes.#

[#norm:Ztt_mldexp_fp]#For a floating-point datatype, the result is rounded as selected by `rm` and saturated as selected by `sat`.#
[#norm:Ztt_mldexp_int]#For an integer datatype, an exponent _e_ {ge} 0 shifts left: the result is the low bits of the shifted value, or the saturated value when `sat` is set.
An exponent _e_ < 0 shifts right by −__e__, arithmetically for a signed datatype and logically for an unsigned one, rounding the discarded bits as selected by `rm`.
A right shift by the element width or more gives the result of shifting out all bits.#

NOTE: With the integer rounding modes, a right shift by insn:mldexp[] is a plain shift for RDN and the rounding shift of the vector extension's insn:vssra.vv[] and insn:vssrl.vv[] for RNU, RNE, and ROD.
The datatype's signedness selects the arithmetic or the logical shift.

[#norm:Ztt_mldexp_types]#insn:mldexp[] supports every integer datatype and every floating-point datatype except E8M0 and TF32.#

In assembly, the third operand is a register name, an X register name, or an immediate, and the flag `mod` follows `rm` and `sat`:

[source,asm]
----
mldexp  acc0.int32, acc0.int32, a5, rnu        # acc0 = acc0 x 2^a5, rounded
mldexp  acc1.int32, acc1.int32, -7, rnu        # constant shift right by 7
mldexp  m2.bf16, m2.bf16, m4.int16             # per-element scaling
----

[NOTE]
====
The register form serves kernels that receive the shift at run time.
Library kernels, such as those of XNNPACK, are compiled once for all layers and take the requantization shift as a parameter, and dynamic quantization computes it while the program runs.

The immediate form serves kernels specialized for one layer, and scaling by a constant power of two.
It saves a register and the instruction that loads it, and it reads no X register, so a decoupled matrix unit receives the operand with the instruction.
====

[[ztt-ops-mexp2]]
===== Exponentials

[#norm:Ztt_mexp2]#insn:mexp2[] computes 2^__x__^ of each element _x_ of its source.
The source and destination datatypes are equal, and are FP16, BF16, or FP32.#
[#norm:Ztt_mexp2_acc]#A result is 2^__x__^ if that is representable, and otherwise one of the two representable values adjacent to it; which one is implementation-defined, and depends only on _x_ and the datatype.#
[#norm:Ztt_mexp2_special]#2^+{inf}^ is +{inf}, 2^−{inf}^ is +0, and a NaN gives the canonical NaN.
A result beyond the largest finite value is +{inf}, or the largest finite value as selected by `sat`.
The floating-point exception flags accrue as for a rounded result: NV for a signaling NaN, OF and UF for overflow and underflow, and NX for an inexact result.
An `rm` other than 0 is reserved.#

NOTE: Faithful rounding admits a table and a short polynomial on the fraction of _x_.
The natural exponential is e^__x__^ = 2^__y__^ with _y_ = _x_ log~2~ e, and softmax folds the factor log~2~ e into the scaling of the scores:

[source,asm]
----
msub    m4.fp32, m4.fp32, m6.fp32         # x - max of its row
mmul    m4.fp32, m4.fp32, t0              # t0 holds log2(e), scaled
mexp2   m4.fp32, m4.fp32
----

[[ztt-ops-mrec]]
===== Reciprocal and Reciprocal Square Root

[#norm:Ztt_mrec]#insn:mrec[] computes 1/__x__ and insn:mrsqrt[] computes 1/√__x__ of each element _x_ of its source.
The source and destination datatypes are equal, and are FP16, BF16, or FP32.
A result is rounded as for insn:mexp2[] (<<ztt-ops-mexp2>>).#
[#norm:Ztt_mrec_special]#For insn:mrec[], 1/±0 is ±{inf} and raises DZ, and 1/±{inf} is ±0.
For insn:mrsqrt[], 1/√±0 is ±{inf} and raises DZ, 1/√+{inf} is +0, and a source less than 0 gives the canonical NaN and raises NV.
A NaN gives the canonical NaN, and raises NV if signaling.
A result beyond the largest finite value is ±{inf}, or the largest finite value as selected by `sat`.
The other floating-point exception flags accrue as for insn:mexp2[], and an `rm` other than 0 is reserved.#

NOTE: A quotient _a_/__b__ is _a_ {times} 1/__b__, rounded twice.
Softmax multiplies by the reciprocal of the row sums, and normalization by the reciprocal square root of the variance:

[source,asm]
----
mrec    m6.fp32, m6.fp32                  # m6 holds the sum of each row
mmul    m4.fp32, m4.fp32, m6.fp32         # softmax
madd    m8.fp32, m8.fp32, t0              # variance + epsilon, from t0
mrsqrt  m8.fp32, m8.fp32
mmul    m10.fp32, m10.fp32, m8.fp32       # (x - mean) / sqrt(variance + epsilon)
----

[[ztt-ops-acc]]
===== Operations on Accumulators

[#norm:Ztt_acc_ops]#The elementwise operations of <<ztt-acc-ops-table>> also take accumulator registers as destination and first source, with the second operand forms listed.#

[[ztt-acc-ops-table]]
.Elementwise operations on accumulators.
[%autowidth,float="center",align="center",cols="<,<,<",options="header"]
|===
|Operation |Second operand |Use
|insn:madd[] |accumulator, matrix register, broadcast |Combining results, residual add, bias
|insn:mmul[] |accumulator, broadcast, scalar |Gating, per-channel and per-tensor scale
|insn:msmul[], insn:mldexp[] |scalar, broadcast |Requantization, per tensor or per channel
|insn:mmax[], insn:mmin[] |scalar |ReLU and clamping
|===

[#norm:Ztt_acc_madd_m]#When the second operand of insn:madd[] is a matrix-register operand, it designates a tile as for insn:mcvt[], and its datatype is one that converts exactly to the accumulator datatype; the sum is rounded once.#
[#norm:Ztt_bcast]#A broadcast operand is a vector _v_ of _N_ elements taken from a matrix-register operand that designates a tile as for insn:mcvt[].
In the row form, written with the suffix `.row`, _v_ is row 0 of the tile, and element (_i_, _j_) of the result uses _v_~__j__~; in the column form, written `.col`, _v_ is column 0, and element (_i_, _j_) uses _v_~__i__~.#

NOTE: A load with _LD_ = 0 and a column reduction (<<ztt-ops-reduce>>) write a vector to every row, where the row form reads it; a transposing load with _LD_ = 0 and a row reduction write it to every column, where the column form reads it.

NOTE: The operations of <<ztt-acc-ops-table>> let an accumulator be an operand without a spill to a matrix register; an implementation may execute one by converting the accumulator into an operand that no instruction names and operating on that operand.
Other operations on accumulators, such as GELU, convert to a matrix register with insn:mcvt[] and continue there.

[source,asm]
----
madd.row  acc0.fp32, acc0.fp32, m12x2.fp32     # bias per output column
madd      acc0.fp32, acc0.fp32, m2.bf16        # residual add, widening
mmax      acc0.fp32, acc0.fp32, x0             # ReLU: x0 holds +0.0
mmul      acc2.fp32, acc2.fp32, t0             # scale by 1/sqrt(d), from t0
msmul.row acc1.int32, acc1.int32, m14x2.int32, rmm  # per-channel multiplier
----

[[ztt-ops-cmp]]
===== Compares

[#norm:Ztt_mcmp]#insn:mcmpeq[], insn:mcmpne[], insn:mcmplt[], insn:mcmple[], insn:mcmpgt[], and insn:mcmpge[] compare corresponding elements of two sources of one datatype and write all ones where the comparison holds and zero elsewhere.
The destination datatype is the unsigned integer datatype of the same width.
An `rm` other than 0 and `sat` are reserved for them.#
[#norm:Ztt_mcmp_fp]#For floating-point datatypes, a comparison with a NaN is false except for insn:mcmpne[]; insn:mcmpeq[] and insn:mcmpne[] raise NV for a signaling NaN, and the others for any NaN, as insn:feq.s[], insn:flt.s[], and insn:fle.s[] do.#

NOTE: A mask selects with insn:mand[], insn:mandnot[], or insn:mbsel[].
The two halves of a select by one mask are exact complements, and a NaN goes to the half the choice of comparison sends it to.

[[ztt-ops-bitwise]]
==== Bitwise Operations

[#norm:Ztt_bitwise]#insn:mand[], insn:mandnot[], insn:mor[], insn:mornot[], and insn:mxor[] compute _a_ & _b_, _a_ & ~__b__, _a_ {vbar} _b_, _a_ {vbar} ~__b__, and _a_ ^ _b_.
insn:mbsel[] computes (__a__ & _b_) {vbar} (~__a__ & _d_), where _d_ is the destination element, so that mask _a_ selects bits of _b_ over the destination.#

[#norm:Ztt_mrol]#insn:mrol[] rotates each element of its source left by the corresponding element of a second operand, or by a scalar operand, reduced modulo the element width.#
[#norm:Ztt_bitwise_types]#Bitwise operations operate on matrix-register operands.
Their datatypes are unsigned integer datatypes, which give only the element width; the other datatypes, an `rm` other than 0, and `sat` are reserved for them.#

NOTE: A rotate right by _n_ is a rotate left by −__n__ modulo the element width, so one operation provides both directions.
Rotates serve hashing, checksums, and the permutation of packed fields.

[[ztt-ops-reduce]]
==== Reductions

[#norm:Ztt_red]#insn:mredmax[] and insn:mredmin[] reduce each row or each column of an _N_ {times} _N_ source to its largest or smallest element, and write the result to every element of that row or column of the destination.
In the row form, written `.row`, element (_i_, _j_) of the destination is the reduction of row _i_ of the source; in the column form, written `.col`, of column _j_.#
[#norm:Ztt_red_operands]#The source and destination are both accumulator registers, or both matrix-register operands that designate a tile as for insn:mcvt[], and have one datatype.
The source is read in full before the destination is written.#
[#norm:Ztt_red_fp]#For floating-point datatypes, the reductions are the maximumNumber and minimumNumber operations of IEEE 754-2019, as for insn:mmax[] and insn:mmin[], and raise NV for a signaling NaN.
An `rm` other than 0 and `sat` are reserved for them.#
[#norm:Ztt_red_types]#The reductions support the datatypes of insn:mmax[] and insn:mmin[] (<<ztt-ops-arith>>).#

NOTE: The result is replicated along the reduced dimension, so it is an operand of elementwise operations, which take no broadcasts, and every instruction writes its whole destination.

Sums are matrix multiplies by a matrix of ones, held in a matrix register loaded once.
insn:mmacc[] with ones as B adds the sum of row _i_ of A, over _K_ columns, to every element of row _i_ of C.
With ones as A, it adds the sum of row _j_ of B, which is column _j_ of a matrix loaded with a transposing load, to every element of column _j_ of C.
The sums are computed as specified in <<ztt-ops-mmacc>>, exactly for integer datatypes.

[source,asm]
----
mmacc       acc1.int32, m0x2.int8, m8x2.int8   # m8x2 holds ones: row sums of A
mmacc       acc2.int32, m8x2.int8, m4x2.int8   # m4x2 holds B^T: column sums of B
mcvt        m10x2.fp32, acc0.fp32              # an accumulator is summed from a matrix register
mmacc       acc3.fp32, m10x2.fp32, m12x2.fp32  # m12x2 holds ones
mredmax.row acc4.fp32, acc0.fp32               # row maxima of attention scores
----

NOTE: The row and column sums of the sources are the zero-point corrections of a quantized matrix multiply.

[NOTE]
====
Other reductions are composed from these instructions:

[%autowidth,float="center",align="center",cols="<,<",options="header"]
|===
|Reduction |Composition
|Weighted sum |insn:mmacc[] with the weights in place of ones
|Prefix sum |insn:mmacc[] with a triangular matrix of ones
|Sum of squares, mean |insn:mmul[], then a sum; a sum, then insn:mmul[] by 1/__K__
|Largest magnitude |insn:mredmax[] and insn:mredmin[], a negation, and insn:mmax[]
|Any, all |insn:mredmax[] and insn:mredmin[] of a mask
|Count |A mask ANDed with ones, then a sum
|Index of the maximum |insn:mredmax[], insn:mcmpeq[], insn:mbsel[] of an index matrix, and insn:mredmin[]
|Whole tile |The row form, then the column form
|===
====

[[ztt-ops-mcvt]]
==== Moves and Conversions

[#norm:Ztt_mcvt]#insn:mcvt[] converts element (_r_, _c_) of its source from the source datatype to element (_r_, _c_) of its destination in the destination datatype.
Its source and destination are each a matrix-register operand or an accumulator register; the four combinations have separate encodings.#

[#norm:Ztt_mcvt_tile]#Both operands hold _C_ columns (<<ztt-enc-columns>>), and _C_ is _N_ when either is an accumulator register.
A matrix-register operand of element width _w_ < 16 with _C_ = _N_ is slot _s_ of a register.
An accumulator operand designates an accumulator register, or an accumulator pair for a 64-bit datatype.#
[#norm:Ztt_mcvt_slot]#A slot index of 16/__w__ or more, or a nonzero slot index for an operand that is not a slot, raises an illegal-instruction exception.#
[#norm:Ztt_mcvt_merge]#Writing a slot leaves the other slots of the register unchanged.#
[#norm:Ztt_mcvt_overlap]#The source is read in full before the destination is written, so the two may overlap.#

[#norm:Ztt_mcvt_conv]#A result that is not exactly representable in the destination datatype is rounded as selected by `rm` (<<ztt-rounding>>) and saturated as selected by `sat` (<<ztt-saturation>>).
An integer source is sign-extended if signed and zero-extended if unsigned.#

[#norm:Ztt_mcvt_combos]#insn:mcvt[] supports every pair of datatypes of <<ztt-type-code-table>>, except that E8M0 converts only to and from FP32, INT32, UINT32, INT64, UINT64, and FP64 do not convert to floating-point datatypes narrower than 32 bits, and a 64-bit datatype requires a 64-bit accumulation extension (<<ztt-ext-acc64>>).#

NOTE: Each supported conversion is exact through FP32 or ends in a datatype of 32 bits or more, so a converter with an FP32 internal format rounds once.
Software converts the excluded pairs through FP32.

[source,asm]
----
mcvt  m4[0].e4m3, acc0.fp32                  # FP8 into slot 0, rounding mode DYN
mcvt  m4[1].e4m3, acc1.fp32, rne             # slot 1: m4 is now an N x 2N operand
mcvt  m6[2].int4, acc2.int32, sat            # INT32 to INT4, saturating
mcvt  acc0.fp32, m2.bf16                     # widen a BF16 tile into an accumulator
mcvt  m8x2.bf16, m0.int8                     # C = 2N: a whole INT8 register into BF16
mcvt  acc1.int8, acc1.int32, sat             # in place, for an e8 accumulator store
----

In assembly, the slot index follows the register name in brackets, and is written for every slot operand, including `[0]`.

[NOTE]
====
Integer requantization scales an accumulator, shifts it right with rounding, and narrows it with saturation.
After the scaling multiply, the shift and the narrowing are two instructions:

[source,asm]
----
mldexp  acc0.int32, acc0.int32, a5, rnu        # a5 < 0: round(acc0 x 2^a5)
mcvt    m4[0].int8, acc0.int32, sat            # saturate to INT8
----
====

NOTE: A tile written into slot _s_ forms columns _sN_ to (__s__ + 1)__N__ − 1 of a source operand, so the result of one matrix multiply feeds the next as A without a transpose.

The pseudoinstruction insn:mmv[] copies registers without conversion, using integer datatypes so that every bit is preserved:

[%autowidth,float="center",align="center",cols="<,<",options="header"]
|===
|Pseudoinstruction |Base instruction
|`mmv md, ms` |`mcvt md.uint16, ms.uint16`
|``mmv md``x__G__``, ms``x__G__ |``mcvt md``x__G__``.uint16, ms``x__G__``.uint16``
|`mmv accd, accs` |`mcvt accd.uint32, accs.uint32`
|`mmv mdx2, accs` |`mcvt mdx2.uint32, accs.uint32`
|`mmv accd, msx2` |`mcvt accd.uint32, msx2.uint32`
|===

[[ztt-ops-mmvxm]]
==== Moves Between Matrix and X Registers

[#norm:Ztt_mmvxm]#insn:mmv.x.m[] copies element _k_ of a matrix register to X register `rd`, where _k_ is the value of X register `rs2` and element _k_ is element (⌊__k__/__C__⌋, _k_ mod _C_) of the register, with _C_ = 16__N__/__w__ (<<ztt-mreg-layout>>).
The element width _w_, 8, 16, 32, or 64 bits, is given by the suffix `e8`, `e16`, `e32`, or `e64`; the element is sign-extended to XLEN bits.#
[#norm:Ztt_mmvxm_range]#If _k_ is not less than _NC_, the number of elements in the register, `rd` is written with 0.#
[#norm:Ztt_mmvmx]#insn:mmv.m.x[] writes the low _w_ bits of X register `rs1` to element _k_ of a matrix register, numbered as for insn:mmv.x.m[], where _k_ is the value of X register `rs2`, and leaves the other elements unchanged.
If _k_ is not less than _NC_, no element is written.#
[#norm:Ztt_mmvxm_rv32]#For XLEN = 32, `e64` raises an illegal-instruction exception.#
insn:mmv.x.m[] and insn:mmv.m.x[] are 32-bit instructions (<<ztt-encoding-32>>).

NOTE: insn:mmv.x.m[] is the only Ztt instruction that writes an X register.
A floating-point value continues in an F register through insn:fmv.w.x[] or insn:fmv.d.x[], and an accumulator element is read or written through a matrix register with insn:mcvt[].

[source,asm]
----
mredmax.row acc0.fp32, acc0.fp32             # maximum of each row
mredmax.col acc0.fp32, acc0.fp32             # every element holds the maximum of the tile
mcvt        m4x2.fp32, acc0.fp32
mmv.x.m.e32 a0, m4, x0                       # element 0
fmv.w.x     fa0, a0
mmv.m.x.e32 m4, a1, t1                       # element t1 of m4 = a1
----

[[ztt-ops-const]]
==== Constant Matrices

[#norm:Ztt_mfill]#insn:mfill[] writes the low _w_ bits of X register `rs1` to every element of a matrix register, for an element width _w_ of 8, 16, 32, or 64 bits given by the suffix `e8`, `e16`, `e32`, or `e64`.#
[#norm:Ztt_mid]#insn:mid.row[] and insn:mid.col[] write to element (_r_, _c_) of a matrix-register operand its row number _r_ or its column number _c_, modulo 2^__w__^, for an element width _w_ of 8, 16, 32, or 64 bits given by the suffix.
The operand occupies a group of _G_ = 1, 2, or 4 registers (<<ztt-groups>>), and is an _N_ {times} 16__GN__/__w__ matrix.#
[#norm:Ztt_const_rv32]#For XLEN = 32, insn:mfill[] with `e64` raises an illegal-instruction exception.#
They are 32-bit instructions (<<ztt-encoding-32>>).

NOTE: A value narrower than 8 bits is written by insn:mfill[] with `e8` and the value replicated in each byte, as 0x11 for INT4 ones.

Other constant matrices are composed from these:

[source,asm]
----
li          t0, 0x3f80
mfill.e16   m8, t0                                # BF16 ones
mid.col.e16 m9                                    # m9(r, c) = c, the indices for an argmax
mid.row.e16 m10                                   # m10(r, c) = r
mcmpge      m11.uint16, m9.uint16, m10.uint16     # c >= r
mand        m11.uint16, m11.uint16, m8.uint16     # BF16 ones on and above the diagonal
mcmpeq      m12.uint16, m9.uint16, m10.uint16     # c = r
mand        m12.uint16, m12.uint16, m8.uint16     # BF16 identity
----

[[ztt-sw]]
=== Software Considerations

[[ztt-cc]]
==== Calling Convention

All `m` and `acc` registers are caller-saved: a called function need not preserve them, as for the vector registers and the Intel AMX tile registers.
The RISC-V psABI is the authoritative definition.

[[ztt-example-gemm]]
==== Example: Matrix Multiply with Bias and ReLU

The following code computes one 2__N__ {times} 2__N__ block of C = ReLU(A {times} W^T^ + bias) in BF16, accumulating in FP32 in four accumulators.
W is stored as `[P][K]`, the usual layout of weights, so its rows are the B^T^ that insn:mmacc[] reads.
The code does not depend on _N_.

[source,asm]
----
# a0: &A[i][0]   a1: lda   a2: &W[j][0]   a3: ldw   (leading dimensions in elements)
# a4: &C[i][j]   a5: ldc   a6: K, a multiple of N   a7: &bias[j]

        csrr        t1, amenlenb        # 2N: N BF16 elements are 2N bytes
        srli        t0, t1, 1           # N
        mul         t3, t1, a1
        add         t3, a0, t3          # &A[i+N][0]
        mul         t4, t1, a3
        add         t4, a2, t4          # &W[j+N][0]
        mzero       acc0
        mzero       acc1
        mzero       acc2
        mzero       acc3
1:      mls.st.e16  m0, (a0), a1        # A rows i to i+N-1, next N columns
        add         a0, a0, t1
        mls.st.e16  m1, (t3), a1        # A rows i+N to i+2N-1
        add         t3, t3, t1
        mls.st.e16  m2, (a2), a3        # W rows j to j+N-1
        add         a2, a2, t1
        mls.st.e16  m3, (t4), a3        # W rows j+N to j+2N-1
        add         t4, t4, t1
        mmacc       acc0.fp32, m0.bf16, m2.bf16
        mmacc       acc1.fp32, m0.bf16, m3.bf16
        mmacc       acc2.fp32, m1.bf16, m2.bf16
        mmacc       acc3.fp32, m1.bf16, m3.bf16
        sub         a6, a6, t0
        bnez        a6, 1b

        slli        t2, t1, 1           # N FP32 elements are 4N bytes
        add         t2, a7, t2          # &bias[j+N]
        mls.st.e32  m4x2, (a7)          # bias[j] to bias[j+N-1] in every row
        mls.st.e32  m6x2, (t2)          # bias[j+N] to bias[j+2N-1]
        madd.row    acc0.fp32, acc0.fp32, m4x2.fp32
        madd.row    acc1.fp32, acc1.fp32, m6x2.fp32
        madd.row    acc2.fp32, acc2.fp32, m4x2.fp32
        madd.row    acc3.fp32, acc3.fp32, m6x2.fp32
        mmax        acc0.fp32, acc0.fp32, x0    # ReLU: x0 holds +0.0
        mmax        acc1.fp32, acc1.fp32, x0
        mmax        acc2.fp32, acc2.fp32, x0
        mmax        acc3.fp32, acc3.fp32, x0
        mcvt        acc0.bf16, acc0.fp32        # in place, rounding mode DYN
        mcvt        acc1.bf16, acc1.fp32
        mcvt        acc2.bf16, acc2.fp32
        mcvt        acc3.bf16, acc3.fp32
        msa.st.e16  acc0, (a4), a5      # C[i][j]
        add         t5, a4, t1
        msa.st.e16  acc1, (t5), a5      # C[i][j+N]
        mul         t6, t1, a5
        add         a4, a4, t6
        msa.st.e16  acc2, (a4), a5      # C[i+N][j]
        add         t5, a4, t1
        msa.st.e16  acc3, (t5), a5      # C[i+N][j+N]
----

NOTE: Blocks at the edges of C, and a _K_ that is not a multiple of _N_, use the partial-tile forms of the loads and stores, whose zero fill makes the extra columns contribute nothing.

[[ztt-example-gemm-groups]]
==== Example: Matrix Multiply with Register Groups

Loading register groups reduces the number of loads and address updates per insn:mmacc[].
The following code replaces the loop of <<ztt-example-gemm>>, for a _K_ that is a multiple of 4__N__.
Each load fetches 4__N__ columns into a group of four registers, and each insn:mmacc[] names one register of a group.
The loop ends when the first pointer into A reaches the end of its rows, so it needs no counter.

[source,asm]
----
        slli        t2, t1, 2           # 4N BF16 elements are 8N bytes
        slli        a6, a6, 1
        add         a6, a0, a6          # &A[i][K]
1:      mls.st.e16  m0x4, (a0), a1      # A rows i to i+N-1, next 4N columns
        add         a0, a0, t2
        mls.st.e16  m4x4, (t3), a1      # A rows i+N to i+2N-1
        add         t3, t3, t2
        mls.st.e16  m8x4, (a2), a3      # W rows j to j+N-1
        add         a2, a2, t2
        mls.st.e16  m12x4, (t4), a3     # W rows j+N to j+2N-1
        add         t4, t4, t2
        mmacc       acc0.fp32, m0.bf16, m8.bf16
        mmacc       acc1.fp32, m0.bf16, m12.bf16

        mmacc       acc3.fp32, m4.bf16, m12.bf16
        mmacc       acc0.fp32, m1.bf16, m9.bf16
        mmacc       acc1.fp32, m1.bf16, m13.bf16
        mmacc       acc2.fp32, m5.bf16, m9.bf16

[[ztt-example-softmax]]
==== Example: Softmax

The following code computes Y = softmax(X) for _N_ rows of _L_ FP32 elements, normalizing each row, for an _L_ that is a multiple of _N_.
It processes _N_ {times} _N_ tiles, each in a group of two registers, in three passes: the maximum of each row, the sum of the exponentials of each row, and the normalized exponentials.
For the row maximum _m_, it computes e^__y__^ for _y_ = _x_ − _m_ as 2^__z__^ for _z_ = _y_ log~2~ e; row maxima and row sums are replicated along each row, so they combine elementwise with the tiles.

[source,asm]
----
# a0: &X[i][0]   a1: ldx   a2: &Y[i][0]   a3: ldy   (leading dimensions in elements)
# a4: L, a multiple of N

        csrr        t1, amenlenb        # 2N
        slli        t2, t1, 1           # N FP32 elements are 4N bytes
        slli        a4, a4, 2
        add         a4, a0, a4          # &X[i][L]
        li          t3, 0x3fb8aa3b      # log2(e) in FP32
        li          t4, 0xff800000      # -infinity
        mfill.e32   m2, t4
        mfill.e32   m3, t4
        li          t4, 0x3f800000      # 1.0
        mfill.e32   m4, t4
        mfill.e32   m5, t4              # m4x2: ones

        mv          t5, a0              # pass 1: row maxima
1:      mls.st.e32  m0x2, (t5), a1
        add         t5, t5, t2
        mmax        m2.fp32, m2.fp32, m0.fp32
        mmax        m3.fp32, m3.fp32, m1.fp32
        bne         t5, a4, 1b
        mredmax.row m2x2.fp32, m2x2.fp32
        mmul        m2.fp32, m2.fp32, t3    # m log2(e)
        mmul        m3.fp32, m3.fp32, t3

        mzero       acc0                # pass 2: row sums
        mv          t5, a0
2:      mls.st.e32  m0x2, (t5), a1
        add         t5, t5, t2
        mmul        m0.fp32, m0.fp32, t3
        mmul        m1.fp32, m1.fp32, t3
        msub        m0.fp32, m0.fp32, m2.fp32
        msub        m1.fp32, m1.fp32, m3.fp32
        mexp2       m0.fp32, m0.fp32
        mexp2       m1.fp32, m1.fp32
        mmacc       acc0.fp32, m0x2.fp32, m4x2.fp32 # adds the row sums to every column
        bne         t5, a4, 2b
        mcvt        m6x2.fp32, acc0.fp32
        mrec        m6.fp32, m6.fp32
        mrec        m7.fp32, m7.fp32

3:      mls.st.e32  m0x2, (a0), a1      # pass 3: normalized exponentials
        add         a0, a0, t2
        mmul        m0.fp32, m0.fp32, t3
        mmul        m1.fp32, m1.fp32, t3
        msub        m0.fp32, m0.fp32, m2.fp32
        msub        m1.fp32, m1.fp32, m3.fp32
        mexp2       m0.fp32, m0.fp32
        mexp2       m1.fp32, m1.fp32
        mmul        m0.fp32, m0.fp32, m6.fp32
        mmul        m1.fp32, m1.fp32, m7.fp32
        mss.st.e32  m0x2, (a2), a3
        add         a2, a2, t2
        bne         a0, a4, 3b
----

The third pass computes the exponentials again instead of loading them stored by the second, which trades three instructions per register for a store of each tile.

[[ztt-example-flash]]
==== Example: Flash Attention

The following code computes O = softmax(__s__ Q K^T^) V for a block of _N_ query rows in BF16, with a head dimension _d_ = 4__N__, in one pass over _L_ keys and values, as the forward pass of FlashAttention-2.
For each block of _N_ keys, it raises the row maxima _m_, rescales the row sums _l_ and the output by α = 2^__a__^ for _a_ = __m__~old~ − __m__~new~, and adds the new block's contributions; it divides by _l_ once at the end.
The output stays in four accumulators, the scores use a fifth, and the row sums a sixth; α and 1/__l__, replicated along each row, scale them as column broadcasts.

[source,asm]
----
# a0: &Q[i][0]   a1: ldq   a2: &K[0][0]   a3: ldk   a4: &V[0][0]   a5: ldv
# a6: &O[i][0]   a7: L, a multiple of N   s0: ldo   (leading dimensions in elements)
# s1: s log2(e) in FP32, for the scale s of the scores

        csrr        t1, amenlenb        # 2N
        mul         t2, t1, a3          # N rows of K
        mul         t3, t1, a5          # N rows of V
        mul         t5, a7, a3
        slli        t5, t5, 1
        add         t5, a2, t5          # &K[L][0]
        mls.st.e16  m0x4, (a0), a1      # Q: N rows, 4N columns
        li          t4, 0xff800000      # -infinity
        mfill.e32   m16, t4
        mfill.e32   m17, t4             # m16x2: running row maxima
        li          t4, 0x3f800000      # 1.0
        mfill.e32   m20, t4
        mfill.e32   m21, t4             # m20x2: ones
        mzero       acc0
        mzero       acc1
        mzero       acc2
        mzero       acc3                # acc0 to acc3: output
        mzero       acc5                # row sums

1:      mls.st.e16  m4x4, (a2), a3      # N keys
        add         a2, a2, t2
        mls.tst.e16 m8, (a4), a5        # V^T: N columns of N values
        add         t6, a4, t1
        mls.tst.e16 m9, (t6), a5
        add         t6, t6, t1
        mls.tst.e16 m10, (t6), a5
        add         t6, t6, t1
        mls.tst.e16 m11, (t6), a5
        add         a4, a4, t3
        mzero       acc4
        mmacc       acc4.fp32, m0.bf16, m4.bf16     # scores
        mmacc       acc4.fp32, m1.bf16, m5.bf16
        mmacc       acc4.fp32, m2.bf16, m6.bf16
        mmacc       acc4.fp32, m3.bf16, m7.bf16
        mmul        acc4.fp32, acc4.fp32, s1
        mcvt        m12x2.fp32, acc4.fp32
        mredmax.row m14x2.fp32, m12x2.fp32
        mmax        m14.fp32, m14.fp32, m16.fp32    # new row maxima
        mmax        m15.fp32, m15.fp32, m17.fp32
        msub        m18.fp32, m16.fp32, m14.fp32
        msub        m19.fp32, m17.fp32, m15.fp32
        mexp2       m18.fp32, m18.fp32              # alpha, 0 for the first block
        mexp2       m19.fp32, m19.fp32
        msub        m12.fp32, m12.fp32, m14.fp32
        msub        m13.fp32, m13.fp32, m15.fp32
        mexp2       m12.fp32, m12.fp32              # P
        mexp2       m13.fp32, m13.fp32
        mmv         m16x2, m14x2
        mmul.col    acc5.fp32, acc5.fp32, m18x2.fp32
        mmacc       acc5.fp32, m12x2.fp32, m20x2.fp32   # l = alpha l + row sums of P
        mmul.col    acc0.fp32, acc0.fp32, m18x2.fp32
        mmul.col    acc1.fp32, acc1.fp32, m18x2.fp32
        mmul.col    acc2.fp32, acc2.fp32, m18x2.fp32
        mmul.col    acc3.fp32, acc3.fp32, m18x2.fp32
        mcvt        m22.bf16, m12x2.fp32
        mmacc       acc0.fp32, m22.bf16, m8.bf16    # O = alpha O + P V
        mmacc       acc1.fp32, m22.bf16, m9.bf16
        mmacc       acc2.fp32, m22.bf16, m10.bf16
        mmacc       acc3.fp32, m22.bf16, m11.bf16
        bne         a2, t5, 1b

        mcvt        m12x2.fp32, acc5.fp32
        mrec        m12.fp32, m12.fp32
        mrec        m13.fp32, m13.fp32
        mmul.col    acc0.fp32, acc0.fp32, m12x2.fp32   # O / l
        mmul.col    acc1.fp32, acc1.fp32, m12x2.fp32
        mmul.col    acc2.fp32, acc2.fp32, m12x2.fp32
        mmul.col    acc3.fp32, acc3.fp32, m12x2.fp32
        mcvt        acc0.bf16, acc0.fp32
        mcvt        acc1.bf16, acc1.fp32
        mcvt        acc2.bf16, acc2.fp32
        mcvt        acc3.bf16, acc3.fp32
        msa.st.e16  acc0, (a6), s0      # O[i][0]
        add         a6, a6, t1
        msa.st.e16  acc1, (a6), s0      # O[i][N]
        add         a6, a6, t1
        msa.st.e16  acc2, (a6), s0      # O[i][2N]
        add         a6, a6, t1
        msa.st.e16  acc3, (a6), s0      # O[i][3N]
----

Each block of keys takes nine insn:mmacc[], eight for the products Q K^T^ and P V and one for the row sums, five loads, and 21 other matrix instructions, using 23 matrix registers and six accumulators.
With a seventh accumulator, the scores of the next block are computed while the current block completes.
For training, the forward pass also stores _m_ and _l_ of each row, from which the backward pass recomputes P.

[[ztt-example-attn-2p]]
==== Example: Attention in Two Passes

Flash attention (<<ztt-example-flash>>) rescales its output and row sums in every block of keys, so that its scores never reach memory.
The following code instead stores the scores of a block of queries and finds their maxima first, so that nothing is rescaled, at the cost of storing and loading two scratch tiles per block, and computes the same O for a head dimension _d_ = 8__N__:

* Pass 1 computes S^T^ = K Q^T^, one key per row and one query per column, keeps a running maximum elementwise, and stores S^T^ in BF16.
One insn:mredmax.col[] then gives the maximum _m_ of each query down its column.
* Pass 2a computes P̃^T^, the exponentials 2^__x__^ of the elements _x_ of S^T^ − _m_, sums them elementwise, and stores them with a transposing store, so that each scratch tile holds P̃ with one query per row.
A matrix multiply with an identity matrix (<<ztt-ops-const>>) transposes the sums, so that their row sums _l_ give 1/__l__ in column 0, where the column form of a broadcast reads it.
* Pass 2b computes O = P̃ V in eight accumulators without rescaling, and scales by 1/__l__ once.
Transposing loads supply V^T^, so that insn:mmacc[] computes P̃ (V^T^)^T^.

Q is scaled by _s_ log~2~ e in advance, so no loop operates elementwise on an accumulator.
The scratch buffers hold _L_ {times} _N_ BF16 elements each, as consecutive _N_ {times} _N_ tiles with a leading dimension of _N_.

[source,asm]
----
# a0: &Q[i][0]   a1: ldq   a2: &K[0][0]   a3: ldk   a4: &V[0][0]   a5: ldv
# a6: &O[i][0]   a7: L, a multiple of N   s0: ldo   (leading dimensions in elements)
# s1: s log2(e) in BF16, for the scale s of the scores
# s2: scratch for S^T   s3: scratch for P   (2LN bytes each)

        csrr        t1, amenlenb        # 2N
        srli        t0, t1, 1           # N, the leading dimension of the scratch tiles
        mul         t4, t1, t0          # 2N^2 bytes, one scratch tile
        slli        s5, t1, 2           # 4N BF16 elements are 8N bytes
        mul         t2, t1, a3          # N rows of K
        mul         t3, t1, a5          # N rows of V
        mul         t5, a7, a3
        slli        t5, t5, 1
        add         t5, a2, t5          # &K[L][0]
        mls.st.e16  m0x4, (a0), a1      # Q: N rows, 8N columns
        add         t6, a0, s5
        mls.st.e16  m4x4, (t6), a1
        mmul        m0.bf16, m0.bf16, s1
        mmul        m1.bf16, m1.bf16, s1
        mmul        m2.bf16, m2.bf16, s1
        mmul        m3.bf16, m3.bf16, s1
        mmul        m4.bf16, m4.bf16, s1
        mmul        m5.bf16, m5.bf16, s1
        mmul        m6.bf16, m6.bf16, s1
        mmul        m7.bf16, m7.bf16, s1
        li          t6, 0xff800000      # -infinity
        mfill.e32   m18, t6
        mfill.e32   m19, t6             # m18x2: running maxima

        mv          s4, s2              # pass 1: S^T = K Q^T, running maxima
1:      mls.st.e16  m8x4, (a2), a3      # N keys
        add         t6, a2, s5
        mls.st.e16  m12x4, (t6), a3
        add         a2, a2, t2
        mzero       acc0
        mmacc       acc0.fp32, m8.bf16, m0.bf16     # C[k][q] = sum of K[k][c] Q[q][c]
        mmacc       acc0.fp32, m9.bf16, m1.bf16
        mmacc       acc0.fp32, m10.bf16, m2.bf16
        mmacc       acc0.fp32, m11.bf16, m3.bf16
        mmacc       acc0.fp32, m12.bf16, m4.bf16
        mmacc       acc0.fp32, m13.bf16, m5.bf16
        mmacc       acc0.fp32, m14.bf16, m6.bf16
        mmacc       acc0.fp32, m15.bf16, m7.bf16
        mcvt        m16x2.fp32, acc0.fp32
        mmax        m18.fp32, m18.fp32, m16.fp32
        mmax        m19.fp32, m19.fp32, m17.fp32
        mcvt        m20.bf16, m16x2.fp32
        mss.st.e16  m20, (s4), t0       # S^T tile
        add         s4, s4, t4
        bne         a2, t5, 1b
        mredmax.col m18x2.fp32, m18x2.fp32          # m[k][q] = maximum of query q
        sub         t5, s4, s2
        add         t5, s3, t5          # end of the scratch for P

        mfill.e32   m22, x0
        mfill.e32   m23, x0             # m22x2: sums
        mv          a2, s2              # pass 2a: P^T = 2^(S^T - m), sums
        mv          t6, s3
2:      mls.st.e16  m20, (a2), t0
        add         a2, a2, t4
        mcvt        m16x2.fp32, m20.bf16
        msub        m16.fp32, m16.fp32, m18.fp32
        msub        m17.fp32, m17.fp32, m19.fp32
        mexp2       m16.fp32, m16.fp32
        mexp2       m17.fp32, m17.fp32
        madd        m22.fp32, m22.fp32, m16.fp32
        madd        m23.fp32, m23.fp32, m17.fp32
        mcvt        m21.bf16, m16x2.fp32
        mss.tst.e16 m21, (t6), t0       # P tile, one query per row
        add         t6, t6, t4
        bne         a2, s4, 2b

        li          t6, 0x3f800000      # 1.0
        mfill.e32   m24, t6
        mfill.e32   m25, t6             # m24x2: ones
        mid.row.e32 m28x2
        mid.col.e32 m30x2
        mcmpeq      m26.uint32, m28.uint32, m30.uint32
        mcmpeq      m27.uint32, m29.uint32, m31.uint32
        mand        m26.uint32, m26.uint32, m24.uint32
        mand        m27.uint32, m27.uint32, m25.uint32  # m26x2: identity
        mzero       acc0
        mmacc       acc0.fp32, m26x2.fp32, m22x2.fp32   # transposed: one query per row
        mcvt        m22x2.fp32, acc0.fp32
        mzero       acc0
        mmacc       acc0.fp32, m22x2.fp32, m24x2.fp32   # l_q along row q
        mcvt        m22x2.fp32, acc0.fp32
        mrec        m22.fp32, m22.fp32
        mrec        m23.fp32, m23.fp32

        mzero       acc0                # pass 2b: O = P V, from V^T
        mzero       acc1
        mzero       acc2
        mzero       acc3
        mzero       acc4
        mzero       acc5
        mzero       acc6
        mzero       acc7
3:      mls.st.e16  m20, (s3), t0       # P tile
        add         s3, s3, t4
        mls.tst.e16 m8, (a4), a5        # V^T: N columns of N values
        add         t6, a4, t1
        mls.tst.e16 m9, (t6), a5
        add         t6, t6, t1
        mls.tst.e16 m10, (t6), a5
        add         t6, t6, t1
        mls.tst.e16 m11, (t6), a5
        add         t6, t6, t1
        mls.tst.e16 m12, (t6), a5
        add         t6, t6, t1
        mls.tst.e16 m13, (t6), a5
        add         t6, t6, t1
        mls.tst.e16 m14, (t6), a5
        add         t6, t6, t1
        mls.tst.e16 m15, (t6), a5
        add         a4, a4, t3
        mmacc       acc0.fp32, m20.bf16, m8.bf16
        mmacc       acc1.fp32, m20.bf16, m9.bf16
        mmacc       acc2.fp32, m20.bf16, m10.bf16
        mmacc       acc3.fp32, m20.bf16, m11.bf16
        mmacc       acc4.fp32, m20.bf16, m12.bf16
        mmacc       acc5.fp32, m20.bf16, m13.bf16
        mmacc       acc6.fp32, m20.bf16, m14.bf16
        mmacc       acc7.fp32, m20.bf16, m15.bf16
        bne         s3, t5, 3b

        mmul.col    acc0.fp32, acc0.fp32, m22x2.fp32   # O / l
        mmul.col    acc1.fp32, acc1.fp32, m22x2.fp32
        mmul.col    acc2.fp32, acc2.fp32, m22x2.fp32
        mmul.col    acc3.fp32, acc3.fp32, m22x2.fp32
        mmul.col    acc4.fp32, acc4.fp32, m22x2.fp32
        mmul.col    acc5.fp32, acc5.fp32, m22x2.fp32
        mmul.col    acc6.fp32, acc6.fp32, m22x2.fp32
        mmul.col    acc7.fp32, acc7.fp32, m22x2.fp32
        mcvt        acc0.bf16, acc0.fp32
        mcvt        acc1.bf16, acc1.fp32
        mcvt        acc2.bf16, acc2.fp32
        mcvt        acc3.bf16, acc3.fp32
        mcvt        acc4.bf16, acc4.fp32
        mcvt        acc5.bf16, acc5.fp32
        mcvt        acc6.bf16, acc6.fp32
        mcvt        acc7.bf16, acc7.fp32
        msa.st.e16  acc0, (a6), s0      # O[i][0]
        add         a6, a6, t1
        msa.st.e16  acc1, (a6), s0      # O[i][N]
        add         a6, a6, t1
        msa.st.e16  acc2, (a6), s0
        add         a6, a6, t1
        msa.st.e16  acc3, (a6), s0
        add         a6, a6, t1
        msa.st.e16  acc4, (a6), s0
        add         a6, a6, t1
        msa.st.e16  acc5, (a6), s0
        add         a6, a6, t1
        msa.st.e16  acc6, (a6), s0
        add         a6, a6, t1
        msa.st.e16  acc7, (a6), s0      # O[i][7N]
----

Per block of keys, the passes take the eight insn:mmacc[] of pass 1 and the eight of pass 2b, and 13 other matrix instructions besides loads and stores, none of which operates elementwise on an accumulator.
Pass 2b holds only the output in accumulators, so eight cover _d_ = 8__N__ with the values read once.

NOTE: Scratch tiles in BF16 round the scores before the exponential, which the single-pass form does not; FP32 tiles avoid this at twice their traffic.
Scaling Q in BF16 rounds the scaled queries.
