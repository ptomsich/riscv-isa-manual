[[ext:ssdtso]]
=== ext:ssdtso[] Extension for Dynamic Switching of TSO Memory Ordering


The Ssdtso extension adds a 'dynamic-TSO' mode of operation.
It is intended for implementations whose native memory model is RVWMO; its coexistence with Ztso is specified in <<ssdtso-dependencies-and-incompatibilities>>.

Software executing at a higher privilege level (refer to Section "Privilege Modes" of "The RISC-V Instruction Set Manual: Volume II: Privileged Architecture" for the applicable definition in the presence of the H extension) can enable dynamic-TSO for all lower privilege levels on a per-hart granularity.
Ssdtso does not control the memory ordering of M-mode: the `DTSO` bits never place M-mode in dynamic-TSO mode.
On an implementation that does not implement Ztso, M-mode therefore always executes under RVWMO.
On an implementation that also implements Ztso — where RVTSO is always-on for the whole hart — M-mode executes under RVTSO regardless of Ssdtso.

[NOTE]
====
Ssdtso is intended to provide a compatibility mode to execute binaries that require RVTSO on processors that prefer (e.g., for performance reasons) to be operated in RVWMO mode.
====

The intended use-cases for Ssdtso are

. the execution of individual binaries compiled for RVTSO in user-mode or virtualized user-mode on a processor otherwise operating in RVWMO;
. the execution of operating system images compiled for RVTSO mode in supervisor- and user-mode on a processor otherwise operating in RVWMO;
. the execution of guest operating system images compiled for RVTSO mode in virtualized supervisor- and virtualized user-mode on processors otherwise operating in RVWMO; and
. the execution of binaries dynamically translated from a TSO architecture (e.g., x86), where the translated threads require RVTSO semantics while the translator runtime and native threads of the same process execute under RVWMO (see the per-thread configuration in <<ssdtso-configurations-for-dynamic-tso>>).

Throughout this document, software is said to be _designated_ as requiring RVTSO when the software controlling its execution has determined that it must run under RVTSO semantics — for example, from its ELF flags or through an explicit request (see <<runtime_linker_support>>).

[[ssdtso-interoperability-between-rvtso-and-rvwmo]]
==== Interoperability between RVTSO and RVWMO

RVTSO (whether statically selected or dynamically enabled) makes the following adjustments to RVWMO:

* All load operations behave as if they have an acquire-RCpc annotation.
* All store operations behave as if they have a release-RCpc annotation.
* All AMO operations behave as if they have both acquire-RCsc and release-RCsc annotations.

Because every load carries acquire-RCpc and every store release-RCpc ordering, these annotations subsume the rules for preserved program order (as defined in Section "Preserved Program Order" of "The RISC-V Instruction Set Manual: Volume I"), other than those governing explicit synchronization.
They do so while preserving the single relaxation that distinguishes RVTSO from sequential consistency: a store followed in program order by a load of a different address remains unordered, exactly as RCpc release/acquire pairs permit.

[NOTE]
====
RVWMO is multi-copy atomic, and RISC-V's RCpc annotations are defined within that multi-copy-atomic model.
Unlike the processor-consistent release/acquire accesses of some other architectures — where RCpc is the mechanism that introduces non-multi-copy-atomic behaviour — RISC-V RCpc does not weaken multi-copy atomicity.
RVTSO, and hence dynamic-TSO, is therefore multi-copy atomic, which is what allows a dynamic-TSO hart and an RVWMO hart to share memory without store-atomicity anomalies.
====

Any execution of a system in which some harts operate under dynamic-TSO is a valid RVWMO execution of the same system in which those harts' memory instructions carry the annotations listed above.
Mixed-mode operation therefore introduces no behaviour that RVWMO does not already permit for the annotated program, and the behaviours a dynamic-TSO hart can exhibit are a subset of those RVWMO permits for the same instructions.
Because the floor is identical to the Ztso annotation assignment, compiler mappings of language-level memory models that are correct under Ztso remain correct under dynamic-TSO, and the psABI's interoperability of the RVWMO and Ztso atomics mappings extends to processes designated for dynamic-TSO (see <<ssdtso-compatibility-with-rvwmo-binaries-and-libraries>>).

For the interoperability between code (from different processes) concurrently executing under RVTSO and RVWMO rules (on separate harts), we can therefore assume correct interoperability without any special precautions if the processes use explicit synchronization primitives as required for their respective memory consistency models — for the processes executing under RVWMO semantics, the `FENCE`-based acquire/release sequences and RCsc-annotated atomics (`.aq`/`.rl`) prescribed by the mapping guidelines (see Section "Code Porting and Mapping Guidelines" of "The RISC-V Instruction Set Manual: Volume I").

Ssdtso assumes that the privileged software controlling the dynamic-TSO behaviour is developed for RVWMO and will use such explicit synchronization — `FENCE` instructions and RCsc-annotated atomics — as required.

[NOTE]
====
RISC-V has no RCpc-annotated load or store encodings: RCpc annotations exist only as implicit assignments in the memory model (per Ztso, and per the dynamic-TSO floor defined by this extension).
RVWMO software therefore expresses acquire and release ordering through `FENCE` sequences and the RCsc `.aq`/`.rl` bits on AMOs and `LR`/`SC`.
====

[[ssdtso-dependencies-and-incompatibilities]]
==== Dependencies and Incompatibilities

For its intended use case (i.e., to provide an on-demand RVTSO execution capability for processors otherwise operating in RVWMO), Ssdtso will be used on cores that do not implement Ztso.

However, the Ssdtso extension does not conflict with Ztso (i.e., a core that operates in RVTSO mode at all times) and can be implemented on such a core for compatibility:

* the RVTSO mode is always-on on Ztso implementations, and
* the `DTSO` bit in `menvcfg`, `senvcfg`, and `henvcfg` will accurately reflect whether the core currently operates in RVTSO mode.

[NOTE]
====
It is strongly recommended (but not required) to implement the A extension for synchronization between software executing in RVWMO mode and RVTSO mode (such as S-mode software executing in RVWMO mode and user-space processes executing under dynamic-TSO).

To allow the free composition of extensions for unforeseen use-cases, no formal dependency is introduced and any such mandate is delegated to ISA Profiles or Platforms definition.
====

It is strongly recommended that Ssdtso be implemented uniformly across all harts exposed to a single supervisor-level software image.
As above, no formal requirement is introduced and a uniformity mandate is delegated to ISA Profiles or Platforms definitions.

[NOTE]
====
On a system where only a subset of the harts implements Ssdtso, a thread of a designated process that executes on a hart without Ssdtso runs under RVWMO with its synchronization statically elided — a silent correctness failure.
The scheduling obligation this imposes on the operating system is stated in the <<req-capable>>.
====

[[ssdtso-state-controlling-whether-dynamic-tso-is-enabled]]
==== State controlling whether dynamic-TSO is enabled

The dynamic-TSO behaviour is controlled by bit 8 (`DTSO`) of `menvcfg`, `senvcfg`, and `henvcfg` for all lower privilege levels.
Implementations providing Ssdtso initialize the `DTSO` bit according to their default memory mode:

* implementations that implement only Ssdtso, and not Ztso, default to use RVWMO semantics natively: the bits controlling dynamic-TSO behaviour are initialized to 0 on reset
* implementations that implement both Ssdtso and Ztso, default to use RVTSO semantics natively: the bits controlling dynamic-TSO behaviour are initialized to 1 on reset

If the `DTSO` bit in an `envcfg` CSR is set, the lower-privilege modes indicated in the following table operate in dynamic-TSO mode:
[cols="^3,^2,^1,^1,^1,^1,^1",stripes=even,options="header"]
|===
1+|`DTSO` bit |Virtualization state 5+|Controls dynamic-TSO in modes
|||M|S/HS|U|VS|VU
|menvcfg|n/a|0|1|1|1|1
|henvcfg|n/a|0|0|0|1|1
|senvcfg|V=0|0|0|1|0|0
|senvcfg|V=1|0|0|0|0|1
|===

Each `DTSO` bit is an independently readable and writable WARL field: writing one `envcfg.DTSO` does not affect the others, and the written value is returned on read-back.
On an implementation that also implements Ztso — where RVTSO is always-on for the whole hart — each `DTSO` bit is instead a WARL field whose only legal value is 1: it reads as 1 regardless of the value written, so that it accurately reflects the always-active RVTSO mode.
The _effective_ dynamic-TSO state of a privilege level is the logical OR of the `DTSO` bits that control that level in the table above — a level operates in dynamic-TSO mode whenever any of its controlling `envcfg.DTSO` bits is set.

Consequently a more-privileged level that sets its `DTSO` bit forces dynamic-TSO on all the levels it controls (`menvcfg.DTSO` over S/HS, U, VS, and VU; `henvcfg.DTSO` over VS and VU), and clearing a less-privileged `DTSO` bit cannot disable dynamic-TSO for a level that a more-privileged bit has enabled — even though the cleared bit still reads back as written.

Ssdtso adds no state-enable control of its own: access to the `DTSO` bits follows access to their containing `senvcfg`/`henvcfg` CSR, which is already governed by the ENVCFG bit of `mstateen0` (and, under the H extension, `hstateen0`), so that where a higher privilege level withholds `envcfg` access from a lower one, the `DTSO` bit is likewise inaccessible.

[[ssdtso-interpretation-of-memory-operations-in-dynamic-tso]]
==== Interpretation of memory-operations in dynamic-TSO

While executing instructions in dynamic-TSO mode, every memory instruction is interpreted as carrying at least the memory-ordering annotation that RVTSO assigns to its access class — the dynamic-TSO _ordering floor_:

* every load (including `LR`) behaves as if it had at least an acquire-RCpc annotation;
* every store (including `SC`) behaves as if it had at least a release-RCpc annotation;
* every AMO behaves as if it had at least both acquire-RCsc and release-RCsc annotations.

This is exactly the annotation assignment that the Ztso extension defines (see Section "Ztso Extension for Total Store Ordering" of "The RISC-V Instruction Set Manual: Volume I"); dynamic-TSO neither weakens nor strengthens it.

[NOTE]
====
The floor does not raise an unannotated `LR`/`SC` sequence to the full ordering of an AMO: `LR` and `SC` receive only the RCpc annotations of their load and store classes, exactly as under Ztso.
Code ported from architectures whose atomic read-modify-writes are fully ordered obtains that ordering from the explicit RCsc annotations that the standard mappings place on the instructions (`amo<op>.aqrl`, or `lr.aq; ...; sc.aqrl`; see the Section "Code Porting and Mapping Guidelines" of "The RISC-V Instruction Set Manual: Volume I"), not from the dynamic-TSO floor.
====

This floor applies whether or not the instruction is otherwise annotated.
Where the instruction's encoding already carries an ordering annotation, the ordering imposed on the instruction is the union of that annotation and the floor; an instruction is never ordered more weakly than either.

The floor applies only to accesses to main-memory regions, whose ordering is governed by RVWMO.
Accesses to I/O regions are unaffected: their ordering continues to follow their Physical Memory Attributes (PMAs) and any explicit `FENCE` instructions, exactly as under RVWMO.
Ordering between a main-memory access performed under dynamic-TSO and an access to an I/O region therefore still requires an explicit `FENCE` carrying the appropriate I/O predecessor and successor bits.

[NOTE]
====
A binary that requires ordered access to a device should map that device to a strongly-ordered I/O region through its PMAs; such a region is ordered independently of whether the hart is operating in dynamic-TSO mode.
Dynamic-TSO does not, by itself, impose ordering on relaxed I/O regions.
====

Different harts in a system may operate in different modes.
The mode that applies to each individual instruction — and the semantics of entering and leaving dynamic-TSO mode — are defined in <<transition_semantics>>.

[[transition_semantics]]
==== Semantics of entering and leaving dynamic-TSO mode

A transition into or out of dynamic-TSO mode occurs either
(a) explicitly, through a write to the controlling `menvcfg`, `senvcfg`, or `henvcfg` CSR, or
(b) implicitly, through a change of privilege level (e.g., a trap or an `xRET` instruction) that selects a privilege level operating under a different mode.

Neither form of transition implies a memory fence.
The write to the `envcfg` CSR that toggles the `DTSO` bit is an ordinary control-register write; it does not, by itself, order memory accesses that precede it in program order with respect to those that follow it.
Likewise, a change of privilege level that causes a transition does not, by itself, impose any additional memory ordering beyond that already required by RVWMO.

A hart always observes its own prior stores, regardless of the ordering annotation under which those stores were performed.
Consequently, no fence is required at a mode transition for the correctness of memory accesses performed by the transitioning hart itself.

Because the effective dynamic-TSO state is monotone with privilege — a less-privileged level is controlled by a superset of the `DTSO` bits that control any more-privileged level, and so is always at least as strongly ordered — only a transfer of control to a _less_-privileged level can strengthen the mode in effect.
A trap, which raises privilege, therefore never places an instruction under a stronger mode than the one already in effect and requires no special treatment.
The mode applied to a memory instruction is the effective dynamic-TSO state of the privilege level at which that instruction executes: every instruction executed at a level operating in dynamic-TSO mode observes that level's mode, and no instruction executed there may be observed to use the previously-effective (weaker) mode — including the instructions reached by an `xRET` that lowers privilege into a dynamic-TSO level.
The `DTSO`-changing CSR write itself needs no special treatment, as it does not alter the mode in which the writing, more-privileged software executes.

This requirement determines only which mode applies to each instruction; it is not a memory fence and imposes no memory ordering beyond that of the modes themselves.

The annotations that dynamic-TSO assigns are enforced by the same architectural rules as encoded annotations, and their assignment follows program order under all circumstances: an implementation that executes instructions speculatively must ensure that every memory access retires with (at least) the annotations of the mode in effect at its program-order position, including accesses that were already in flight when a mode transition resolved.

[NOTE]
====
On an implementation that processes instructions out of program order, instructions that follow a `DTSO`-changing CSR write or a mode-changing `xRET` in program order may be in flight before the transition resolves; a simple implementation strategy is to flush younger in-flight instructions when an effective `DTSO` state changes.
Speculative reordering beyond the architectural mode, with misspeculation detection and replay before retirement, remains permitted exactly as it is for encoded acquire/release annotations under RVWMO; Ssdtso introduces no new class of transient-execution behaviour beyond existing memory-ordering speculation.
The security implications of a stale-mode window are discussed in <<security_considerations>>.
====

Memory accesses performed under RVWMO semantics before entering dynamic-TSO mode retain their (weaker) RVWMO ordering.
Software that requires such accesses to be ordered — as observed by other harts — with respect to accesses performed after entering dynamic-TSO mode must insert an explicit `FENCE` instruction.
The software controlling the dynamic-TSO behaviour is expected to provide such explicit ordering where required; where that software itself executes in dynamic-TSO mode or under Ztso (e.g., a guest operating system controlling its user space), the required ordering is already provided by its own, stronger mode.

[NOTE]
====
A mode transition for a lower privilege level is always mediated by higher-privilege software: the `DTSO` bit that governs a privilege level is held in the `envcfg` CSR of a strictly more privileged level, which itself executes under RVWMO or a stronger mode.
An instruction stream that is switched into or out of dynamic-TSO mode therefore never contains the controlling CSR write itself; the write is performed by the more privileged handler and the affected instructions resume, in the new mode, program-order-after the write (including across an intervening `xRET`).
No memory fence is architecturally necessary to make the new mode effective for those instructions.

Where ordering of one hart's pre-transition accesses with respect to its own post-transition accesses is genuinely required, a single `fence rw,rw` placed anywhere in the transition sequence on that hart is sufficient — its position and the privilege level at which it executes do not matter, as `fence rw,rw` orders all preceding memory accesses on the hart with respect to all following ones.
Such a fence orders only the fencing hart's own accesses; it does not cause a concurrently-executing sibling hart to adopt the new mode.
When more than one hart of a process transitions, the requirements in <<entering_and_exiting>> apply.
The common context-switch and early process-initialization paths require no such fence.
====

[[sw_considerations]]

==== Software considerations (informative)

This section is informative from the perspective of hardware implementations: it adds no architectural requirements.
The requirements stated in <<entering_and_exiting>> are, however, preconditions for the correctness of the software that uses the extension.

[[ssdtso-switching-to-dynamic-tso-mode]]
===== Switching to dynamic-TSO mode

Depending on the capabilities of the software runtime environment (e.g., whether an operating system is present, and whether dynamically linked executables are supported), dynamic-TSO mode can be entered at process initialization or programmatically during process runtime:

* at process initialization from the ELF loader (e.g., for statically linked executables that have the `EF_RISCV_TSO` flag set in the `e_flags` field of the ELF file header), or
* at runtime using a system call (e.g., if the runtime linker resolves a shared object that has the `EF_RISCV_TSO` flag set in the `e_flags` field of the ELF file header).

Operating systems may follow various implementation strategies to enable dynamic-TSO in the presence of processes that require RVTSO semantics:

. on-demand switching of individual harts into dynamic-TSO for as long as a process requiring RVTSO semantics executes on them
. enabling dynamic-TSO across all harts as long as RVTSO processes are present in the system
. enabling dynamic-TSO across all harts after encountering the first process requiring RVTSO

[NOTE]
====
While the Ssdtso specification was written to support on-demand switching of individual harts into dynamic-TSO mode, it does not prescribe a specific strategy for how the operating system handles the presence of processes requiring RVTSO semantics.

However, the expectation of the specification architects is that an operating system would attempt to reduce the overall time that cores would spend in dynamic-TSO mode.
====

[[ssdtso-configurations-for-dynamic-tso]]
===== Configurations for dynamic-TSO

The architecture provides a single, hart-local control (the `DTSO` bit) together with the program-order interpretation rule defined in <<transition_semantics>>.
Higher-level notions — such as "a process runs under RVTSO" — are software policies layered on top of this hart-local control.
Four configurations are typical:

. *Single-hart.* Dynamic-TSO is enabled on one hart, and a process requiring RVTSO is confined to that hart.
This is the simplest configuration but requires that the process not migrate to a hart operating under RVWMO.

. *Per-process, across all harts.* The operating system establishes dynamic-TSO on whichever hart is about to execute a thread of an RVTSO process, by writing `senvcfg` (respectively `henvcfg` for a virtualized guest) as part of the context switch.
The process then observes uniform RVTSO semantics regardless of which harts its threads occupy.

. *Per-thread.* The operating system establishes dynamic-TSO only for those threads of a process that require it, by writing the controlling `envcfg` CSR at thread-switch time, so that threads of a single process deliberately operate in different modes.
This supports, for example, the dynamic binary translation of a TSO architecture, where translated threads require RVTSO while native threads and the translator's runtime execute under RVWMO.

. *System-wide.* Dynamic-TSO is enabled on all harts for as long as, or once, an RVTSO process is present (see the strategies above).

[NOTE]
====
The <<req-rendezvous>> governs _changing_ the mode of already-running threads; it does not preclude the deliberate, steady-state operation of a process with per-thread modes.
Such mixed operation is sound — any assignment of modes yields a valid RVWMO execution (see <<formal_model>>, property P4) — provided threads in different modes interact through synchronization that is correct under RVWMO, i.e., through the mapping-compatible primitives described in <<ssdtso-compatibility-with-rvwmo-binaries-and-libraries>>.
A thread whose designation is established before it first runs reduces, as always, to the establish-before-run case and needs no rendezvous.
====

Because a change of the `DTSO` bit for U-mode (or VU/VS) is performed through a write to `senvcfg` or `henvcfg`, the per-process configuration does not require a trap to M-mode and adds only a single control-register write to the context switch.

[[entering_and_exiting]]
===== Requirements when entering and exiting dynamic-TSO mode

The following requirements allow software to build the configurations above correctly on top of the hart-local control.

. [[req-establish,establish-before-run requirement]]*Establish the mode before the affected code runs.*
For a process that is already designated as requiring RVTSO, every hart must have `DTSO` established for the relevant privilege level before that hart executes any instruction of the process.
This is satisfied automatically when the operating system writes the controlling `envcfg` CSR before the `xRET` that returns to the process: the process's instructions follow the write in program order and are therefore interpreted in the new mode.
As a result, no thread of such a process is ever executed under RVWMO semantics, even when individual harts are switched on demand.
(Establishing that designation for an already-running, multi-threaded process is a distinct operation, governed by the <<req-rendezvous>>.)

. [[req-capable,capable-hart confinement requirement]]*Designated software must execute only on Ssdtso-capable harts.*
On a system where not every hart implements Ssdtso, the operating system must confine designated software to harts on which the mode can be established, and must treat this confinement as mandatory — taking precedence over user-controlled placement inputs such as inherited CPU affinity — or refuse the designation where it cannot be satisfied.
Establishing the mode is a precondition of executing the software (see the <<req-establish>>); a hart that cannot establish the mode can never satisfy that precondition.

. [[req-remote,remote-establishment requirement]]*Establishing the mode on a remote hart requires cross-hart synchronization.*
When the mode of a hart other than the one performing the change is altered (for example, when enabling dynamic-TSO system-wide, or when preparing a hart to receive a migrated thread), the operating system must ensure — through an inter-processor interrupt and acknowledgement, or through the release/acquire handoff of a run-queue lock — that the target hart has reached the intended mode before the dependent process is executed on it.

. [[req-migration,migration requirement]]*Thread migration.*
Migration reduces to the <<req-establish>> combined with a cross-hart handoff.
The destination hart establishes `DTSO` before resuming the thread — exactly as for any switch into an RVTSO process — so the migrated thread never runs under RVWMO; and the release (source) / acquire (destination) handoff already provided by run-queue locking makes the thread's prior stores, performed with release-RCpc semantics and multi-copy atomic, globally consistent at the point of handoff.

. [[req-maintain,mode-maintenance requirement]]*The mode, once granted, must be maintained.*
For software designated as requiring RVTSO, the effective dynamic-TSO state must be maintained for every instruction of that software, on every hart that executes it, until the software exits or itself requests a transition (which is then governed by the <<req-rendezvous>>).
The controlling software must not withdraw the mode on its own initiative — for example, because a system-wide enablement policy lapses — while designated software still runs: the designated code's ordering was established at compile time, and it can neither detect nor tolerate even a transient weakening.
Conversely, only software that holds the designation may rely on dynamic-TSO semantics (see the note in <<ssdtso-discovery>>).

. [[req-exit,exit requirement]]*Exiting dynamic-TSO mode never harms other RVWMO participants.*
Because the behaviours permitted under RVTSO are a subset of those permitted under RVWMO, returning a hart from dynamic-TSO to RVWMO cannot invalidate any _other_, correctly-synchronized RVWMO observer elsewhere in the system, and memory accesses already performed under RVTSO retain their stronger ordering.
With respect to such other observers the transition requires no additional synchronization and may be deferred.
This property concerns only the rest of the system; coordinating an exit _among the threads of the exiting process itself_, when that process is multi-threaded, is governed by the <<req-rendezvous>> — a process whose threads leave dynamic-TSO at different times passes through the same mixed-mode window as one whose threads enter it at different times.

. [[req-rendezvous,multi-threaded transition requirement]]*Transitioning while multi-threaded requires synchronization.*
A process that is not yet multi-threaded may enter or leave dynamic-TSO mode freely: no synchronization and no fence are required, because the transitioning hart observes its own prior accesses regardless of their annotation and no other hart is observing the process's memory.
A process that is already multi-threaded must, when transitioning in either direction, bring all of its threads to a common point (a rendezvous), establish the target mode on every hart executing one of its threads, and ensure that memory written under the old mode is ordered before any thread resumes under the new mode.
A correctly-constructed rendezvous — for example, the operating system pausing the sibling harts via inter-processor interrupts and acknowledgement, setting `DTSO`, and then resuming — provides both the required cross-hart establishment of the mode and the ordering of prior memory accesses; no additional `FENCE` is then necessary.
Because this rendezvous is comparatively expensive, a process that will require dynamic-TSO should enter it before becoming multi-threaded (see <<runtime_linker_support>>), reducing the transition to the fence-free single-threaded case.

[[ssdtso-impact-on-thread-task-state]]
===== Impact on thread/task state

For operating systems that use on-demand switching of individual harts, the thread/task structures will require an additional field to track the requirement to execute in dynamic-TSO mode.

[[runtime_linker_support]]
===== Runtime linker support

Support for shared objects requires runtime-linker support, which roughly follows this process:

* The capability to support Ssdtso is detected via an OS specific discovery method (e.g., `riscv_hwprobe` with `RISCV_HWPROBE_EXT_SSDTSO` key on Linux).
* The ELF flags on each resolved shared object are evaluated to determine if RVTSO is required.  In case that RVTSO is required, but neither Ztso nor Ssdtso are available, the runtime linker is expected to invoke appropriate error handling and reporting.
* If a shared object that requires RVTSO is loaded into the process and Ssdtso is implemented, the runtime linker signals the OS to enter dynamic-TSO mode via an OS specific interface (e.g., on Linux: using a `prctl(...)` call).

[NOTE]
====
It is recommended to only signal the need to enter dynamic-TSO mode once per process to reduce the number of system calls in consideration of performance.
Given that entering dynamic-TSO is idempotent, no requirement exists to signal it more than once.

Beyond the performance consideration, entering dynamic-TSO mode early — before the process becomes multi-threaded — avoids the need to synchronize the transition across the process's threads; see the requirements in <<entering_and_exiting>>.
====

[[ssdtso-compatibility-with-rvwmo-binaries-and-libraries]]
===== Compatibility with RVWMO binaries and libraries

RVWMO binaries and libraries can safely execute, without modification, while running under RVTSO semantics.
Consequently, no special consideration or guidance is required for these.

Because the dynamic-TSO interpretation floor is identical to the annotation assignment of Ztso (see <<formal_model>>, property P1), every compiler mapping of a language-level memory model (e.g., the C/{cpp} or Java memory models) that is correct under Ztso is equally correct for software designated for dynamic-TSO: each of its instructions executes under exactly the annotations that Ztso would assign.

A single dynamic-TSO process may therefore also combine code compiled against the RVWMO atomics mapping with code compiled against the Ztso atomics mapping — for example, an RVWMO main binary and its system libraries together with a shared object that requires RVTSO (see <<runtime_linker_support>>) — including concurrent operations on the same atomic objects.
The psABI conditions the interoperability of these two mappings on the hardware implementing Ztso (see the atomics mapping tables of the RISC-V ELF psABI specification); under Ssdtso, that condition is equally satisfied by every instruction of the process executing in dynamic-TSO mode.
The same argument covers memory shared between a dynamic-TSO process and an RVWMO process.

[[ssdtso-discovery]]
===== Discovery

The presence of the Ssdtso extension is discovered through the same mechanism as other RISC-V ISA extensions (for example, the platform's hardware-description structures).
Operating systems may expose its availability to lower privilege levels through an OS-specific interface (e.g., `riscv_hwprobe` with a corresponding key on Linux).

[NOTE]
====
What is exposed to less-privileged software should be the designation itself — "this process (or guest) has been granted dynamic-TSO" — and remain distinct from Ztso.
An operating system should not advertise TSO semantics to software it has not designated, and language runtimes should not condition their code generation on the system incidentally operating in TSO: a mode that was never granted may be withdrawn at any time by a policy change at the higher privilege level.

The exception is nested virtualization: an operating system that itself executes under dynamic-TSO — because the hypervisor's `henvcfg.DTSO` (or `menvcfg.DTSO`) places both its VS and VU levels in dynamic-TSO — observes an architecturally TSO machine for all of its execution.
Such a guest may legitimately claim TSO towards its own user space (for example, by advertising Ztso in its guest ISA description), provided the hypervisor maintains the grant for the lifetime of the guest.
The same applies to a non-virtualized operating system whose S/HS and U levels are placed in dynamic-TSO by `menvcfg.DTSO`.
====

[[security_considerations]]
==== Security considerations (informative)

Enabling dynamic-TSO is fail-safe: because the behaviours permitted under RVTSO are a subset of those permitted under RVWMO, placing software that was built for RVWMO into dynamic-TSO mode cannot create a memory-ordering violation.
The security-relevant hazards of this extension all lie in the opposite direction — in withholding or withdrawing the mode from software that requires it, in executing such software where the mode cannot be established, and in the observability of the mode itself.

[[ssdtso-memory-model-downgrade]]
===== Memory-model downgrade

Software compiled for RVTSO has its ordering established at compile time; executed under RVWMO, its elided synchronization manifests as data races.
An attacker who controls a `DTSO` bit that governs a victim can induce such races deliberately — a memory-model downgrade, turning the victim's correct lock-free code into exploitable race conditions (for example, time-of-check/time-of-use windows on lock-free data structures).

Within a single operating system this adds no new capability: the software controlling a `DTSO` bit is strictly more privileged than the software the bit governs and already controls that software's execution entirely.
The boundary of concern is deployments in which the more-privileged level is not trusted by the less-privileged one, most prominently confidential computing: a confidential guest that requires — or has been told it may rely on — RVTSO is exposed to an untrusted hypervisor silently clearing the grant.
In such architectures, the `DTSO` state governing a confidential workload must be part of the workload's trusted, attested configuration — established and locked through the TEE security manager rather than by the untrusted host — and a withdrawal of the mode while the workload runs must be treated as a security violation, not as a policy change.
This is the security restatement of the <<req-maintain>>.

[[ssdtso-placement-on-capable-harts]]
===== Placement on capable harts

On a system where not all harts implement Ssdtso, placement is security-relevant: user-controlled scheduling inputs — such as CPU affinity inherited across `execve` — must not be able to force designated software onto a hart where the mode cannot be established.
The exposure is sharpest where the designated software is more privileged than the attacker, as for a setuid binary requiring RVTSO: induced races then occur in a victim at a higher privilege, not in the attacker's own process.
The <<req-capable>> must therefore take precedence over user-controlled placement, and the designation must be refused where it cannot be satisfied.

[[ssdtso-availability]]
===== Availability

A policy that enables dynamic-TSO system-wide upon the appearance of any RVTSO process hands unprivileged software a system-wide performance lever: any user able to start a trivial RVTSO-flagged binary degrades every hart for all co-located workloads.
Similarly, the rendezvous of the <<req-rendezvous>> is an all-hart interrupt-and-acknowledge operation; where unprivileged software can trigger it repeatedly, it becomes an amplification primitive.
Operating systems should privilege-gate, rate-limit, or account for system-wide enablement and transition rendezvous, and should prefer the per-process or per-thread configurations, whose cost is confined to the harts actually executing designated software.

[[ssdtso-side-channels]]
===== Side channels

The effective dynamic-TSO state is hart-global execution state and is therefore, like other mode state, a potential covert or side channel between contexts that time-share a hart:

* Whether the hart enforces TSO ordering influences the timing of memory-ordering-sensitive code, so a context may be able to infer — or, given control over a `DTSO` bit, modulate — the mode experienced by another context on the same hart.
* Residual mode must not leak from one context into the next: an operating system should establish the incoming context's designated `DTSO` value as part of every context switch (the per-process configuration in <<ssdtso-configurations-for-dynamic-tso>> does this by construction), which both removes ordering ambiguity and denies a mode-based covert channel its persistence across switches.
* The timing difference between the two operating modes is not, in general, removable; the mode of a context should therefore not itself be treated as a secret.

[[ssdtso-transient-execution]]
===== Transient execution

The annotation assignment of dynamic-TSO follows program order even under speculative execution (see <<transition_semantics>>).
Implementations must ensure that a mode transition does not create a stale-mode window in which accesses that architecturally belong to the new mode execute and retire with the ordering of the old one: such a window would be a transient-execution disclosure gadget, allowing an attacker to observe reorderings that the architectural mode forbids across exactly the privilege boundaries this extension serves.
Beyond this, dynamic-TSO introduces no new class of transient-execution behaviour: speculative reordering with detection and replay before retirement is permitted under dynamic-TSO exactly as it is for encoded acquire/release annotations under RVWMO.

[[ssdtso-scope-of-the-state-enable-gating]]
===== Scope of the state-enable gating

The `mstateen0`/`hstateen0` ENVCFG gating (see <<ssdtso-state-controlling-whether-dynamic-tso-is-enabled>>) is an access-control mechanism only: it determines which privilege level may access a `DTSO` bit, at the granularity of the whole containing `envcfg` CSR — access to `DTSO` cannot be denied separately from the other `envcfg` fields.
It does not, by itself, address the downgrade, placement, or side-channel considerations above, which concern the semantics of the resulting mode rather than access to the controlling bit.

[[formal_model]]
==== Formal model of dynamic-TSO

[[ssdtso-approach]]
===== Approach

Dynamic-TSO is defined entirely as an _annotation-assignment function_ over the existing RVWMO axiomatic model (Chapter "RVWMO Explanatory and Formal Specifications" of "The RISC-V Instruction Set Manual: Volume I").
It adds no relation, no axiom, and no new consistency predicate: the preserved-program-order relation `ppo`, the global memory order `gmo`, and the Load Value, Atomicity, and Progress axioms are used verbatim.
Only the sets that classify an instruction's ordering annotation are redefined, as a union of the instruction's encoded annotation with a mode-dependent floor.

[[ssdtso-mode-predicate]]
===== Mode predicate

For each memory event `e`, let `dtso(e)` hold if and only if the privilege level at which `e` executes is in dynamic-TSO mode, evaluated from the `DTSO` bits in program order at `e` (see <<transition_semantics>>).
Two properties of `dtso` follow directly from the control definition and are relied on below:

* _Well-defined by program order._ `dtso(e)` is a function of the (privilege, `envcfg`) state at `e`'s program-order position; a `DTSO` write reorders no event's classification.
* _Monotone in privilege._ Because a less-privileged level is controlled by a superset of the `DTSO` bits (the effective-OR of <<ssdtso-state-controlling-whether-dynamic-tso-is-enabled>>), `dtso` never decreases as privilege decreases.

[[ssdtso-augmented-annotation-sets]]
===== Augmented annotation sets

Writing `Acq_pc`, `Acq_sc`, `Rel_pc`, and `Rel_sc` for the RVWMO acquire/release-RCpc and acquire/release-RCsc annotation sets, dynamic-TSO replaces them by:

....
Acq_pc' = Acq_pc  ∪  { e ∈ Load   |  dtso(e) }
Rel_pc' = Rel_pc  ∪  { e ∈ Store  |  dtso(e) }
Acq_sc' = Acq_sc  ∪  { e ∈ AMO    |  dtso(e) }
Rel_sc' = Rel_sc  ∪  { e ∈ AMO    |  dtso(e) }
....

Here `Load` includes `LR` events and `Store` includes `SC` events: `LR` and `SC` receive the RCpc floor of their access classes and nothing more, which is exactly the Ztso annotation assignment.
Fully-ordered atomic sequences in ported code carry explicit RCsc annotations (`.aq`/`.rl`) placed by the standard mappings; these enter through the unprimed `Acq_sc`/`Rel_sc` sets unchanged.
`ppo` and `gmo` are then computed from the primed sets; every other definition is unchanged.

[[ssdtso-properties]]
===== Properties

[none]
* *P1 (Reduction to Ztso).* If `dtso(e)` holds for all `e` on every hart, the primed sets equal the Ztso annotation assignment; the model is Ztso.
* *P2 (Reduction to RVWMO).* If `dtso(e)` holds for no `e`, the primed sets equal the encoded sets; the model is RVWMO.
* *P3 (Conservativity).* For any `dtso` labelling, the augmented model is RVWMO evaluated over the same events with the primed annotation sets. No axiom is added or altered.
* *P4 (Monotonicity and composition).* If `dtso ⊆ dtso'` pointwise, then `ppo ⊆ ppo'`, so every `gmo` valid under `dtso'` is valid under `dtso`; hence `allowed(dtso') ⊆ allowed(dtso)`. Taking `dtso'` as a mixed labelling and `dtso` as the empty labelling gives `allowed(mixed) ⊆ allowed(RVWMO)`: any execution of a mixed system is a legal RVWMO execution of the same program with the dtso-annotated events.
* *P5 (Multi-copy atomicity).* `gmo` remains a single total order over memory accesses; the augmentation only constrains it further. Multi-copy atomicity is therefore preserved.

P1 and P2 establish that dynamic-TSO interpolates exactly between RVWMO and Ztso; P4 is the soundness of mixed-mode operation; P5 is the store-atomicity guarantee relied on by cross-mode sharing and by thread migration.

[[ssdtso-validation]]
===== Validation

The augmentation is a localized patch to the machine-readable RVWMO model (the `cat`/Alloy formalisation and its `herd7`/`isla` tooling): redefine the four annotation sets as above, parameterised by a per-event `dtso` flag.
The following litmus tests are checked, each in four configurations — all harts RVWMO, all harts dynamic-TSO, all harts under Ztso, and the mixed labelling shown — with the stated expected verdicts.
By property P1, the dTSO and Ztso columns must be identical on every row: the dTSO verdicts are computed from the model patch of this appendix, the Ztso verdicts from the reference Ztso model, and any divergence between the two columns localizes a defect in the patch.

[cols="3,4,^1,^1,^1,^3",options="header"]
|===
| Test | Probes | WMO | dTSO | Ztso | Mixed (expected)
| SB (plain) | store-to-load reorder | allowed | allowed | allowed | allowed — TSO retains store-to-load
| MP | message passing | allowed | forbidden | forbidden | forbidden iff producer and consumer are both dtso (or carry the equivalent annotations) — a dtso consumer alone cannot order a WMO producer's stores
| SB+LR/SC (Dekker), unannotated | floor on `LR`/`SC` is RCpc only | allowed | allowed | allowed | allowed — the floor does not strengthen `LR`/`SC` beyond Ztso
| SB+LR/SC (Dekker), `lr.aq; sc.aqrl` per the TSO mapping | atomics as fences | forbidden | forbidden | forbidden | forbidden — ordering comes from the encoded RCsc annotations
| IRIW | multi-copy atomicity | forbidden | forbidden | forbidden | forbidden — validates P5
| MP, producer dtso / consumer WMO | cross-mode obligation | n/a | n/a | n/a | allowed unless the consumer uses acquire — validates P4
|===

A test whose mechanized verdict disagrees with this table is a defect in the model patch or in this specification, whichever the discrepancy localizes to.
